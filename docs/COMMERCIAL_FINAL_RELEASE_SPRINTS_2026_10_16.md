# CoreBiz — обязательные спринты до коммерческого релиза

Дата: 16.10.2026  
Репозиторий: venomimonstro/erp-corebiz · ветка: main · без CI/GitHub Actions  
Тип: план работ, а не заявление о выполненном релизе.

## Решение о составе продукта

**CoreBiz — одна многопользовательская система, а не 17 копий ERP.** Должны быть единые источники истины для tenant, пользователя, роли, компании, филиала, клиента, товара/услуги, ресурса, заказа/визита, обязательства, оплаты, складского движения и финансовой проводки. Отраслевой профиль меняет меню, поля, допустимые процессы и требования приёмки.

Наличие файла, контроллера, unit-теста или UI не является доказательством рабочего контура. Каждый спринт закрывается только после **реальной проверки** (или честно помечается NOT RUN / BLOCKED). Все мутирующие API E2E — только на disposable PostgreSQL + Redis. На каждом этапе сохраняется запрет CI/Actions по решению владельца, но локальные и серверные релизные проверки обязательны.

**Что уже заложено исходниками:** tenant/RBAC/RLS, CRM, service booking, dance, товары/склад/OMS/WMS, finance/accounting foundations, биллинг с тарифами, go-live, клиентский портал, import, outbox, release gates. Их нельзя реализовывать с нуля повторно. По предыдущим аудитам 10–13 октября массовый коммерческий GO оставался **NO-GO** до runtime evidence. Платный самостоятельный переход на тариф из billing.selectPlan явно запрещён до провайдерной оплаты.

## Порядок и обязательные критерии готовности

### Этап A. Основа надёжной SaaS (спринты 01–05)

**01 — Воспроизводимая сборка и миграции (P0).** Зафиксировать исходную версию, установить из чистого clone, pnpm lock, typecheck/lint/Jest/build, API+WEB+worker. Replay всех миграций на чистой и исторически обновляемой БД, RLS/SQL функции после upgrade, dry-run и rollback без переименования старых миграций. Выход: полный лог тестов и фактический clean install + upgrade PASS; любое отклонение — блокер релиза.

**02 — Tenant security, роли и персональные данные (P0).** Реальная DB-role без SUPERUSER/BYPASSRLS; user/member/branch scope; права владельца/совладельца, менеджера, тренера, кассира, финансиста, склада и конечного клиента. Проверить смену роли в действующей сессии, отзыв доступа, cross-tenant search/export/API/webhooks, особую защиту данных детей и семейных связей; защита входа, восстановление доступа, MFA для привилегированных ролей, аудит операций и секретов. Выход: 0 подтверждённых утечек и обходов прав по матрице положительных/отрицательных проверок, включая SQL под production DB-role.

**03 — Единая бизнес-модель и полный цикл объектов (P0).** Одни CRM/Party, legal entity, филиал, ресурсы, каталог SKU/услуг, цены и правила, единые операционные документы/обязательства/события. CRUD: создание, список, фильтр, открытие, редактирование, безопасный архив, восстановление по правилам; никакого hard delete с историей. Определить owner/branch/current version/audit/optimistic lock для каждого объекта. Заказ ≠ оплата ≠ отгрузка; визит ≠ оплата; абонемент ≠ признанная выручка. Выход: сквозные аудируемые связи без дублирующей логики и без расхождения между UI/API/ledger.

**04 — Настоящая SaaS-подписка и коммерческий биллинг (P0).** Публичные тарифы и лимиты, trial, оплата выбранного плана у PSP, безопасный webhook+сверка+подписи+идемпотентность, создание/продление подписки, отказ/повтор, upgrade/downgrade, grace/read-only, счета/возвраты, отмена, отсутствие удаления данных. Тариф активируется лишь после подтверждённой оплаты; SaaS-платёж CoreBiz не смешивать с платежами компании-клиента. Выход: sandbox 10 сценариев, включая timeout, duplicate webhook, частичный возврат, неуспешное списание и downgrade; 0 ложных PAID.

**05 — Самостоятельный запуск бизнеса (P0).** Владелец: регистрация → проверка email → пробный тариф/оплата → компания/юрлицо → отрасль → филиалы → команда → каталог → первая операция → go-live. По отрасли показывать только нужные шаги; смешанные профили возможны без дублирования справочников. Импорт и интерактивное исправление ошибок; не путать «первую пользу» и «коммерческую готовность». Выход: новый пользователь без разработчика и админских SQL проходит путь на desktop/mobile, видит блокеры, не попадает в dead end.

### Этап B. Единая операционная система (спринты 06–12)

**06 — Полноценные рабочие места ролей (P0).** Отдельные понятные экраны владельца, администратора, менеджера, тренера, кассира, склада, бухгалтера и клиента. Простое/расширенное меню, быстрые действия, глобальный поиск, сохранённые фильтры, доступная мобильная форма. Каждое действие показывает результат/ошибку и способ восстановления; hidden UI не заменяет API authorization. Выход: полные позитивные и запретные маршруты для каждой роли на телефоне и ПК.

**07 — CRM, клиенты, договоры, задачи и коммуникации (P0).** Общая Party-карточка и семейные связи, организации, сделки, источники, история, договоры, задачи/ответственные, заметки, дедупликация и согласия на уведомления. Связать клиента с заказом, группой, визитом, абонементом, долгом. Смена ответственного не удаляет историю. Выход: менеджер ведёт клиента целиком без повторного ввода, другой клиент/филиал доступен только по правам.

**08 — Универсальные услуги, ресурсы и календарь (P0).** Общие для всех ниш сотрудник/кабинет/зал/оборудование/пост/машина, квалификации, персональная цена и длительность, смены/2-2/отпуск, буферы, вместимость, групповая/индивидуальная запись, аренда помещения, публичная запись, перенос, отмена, неявка. Backend проверяет те же правила при поиске слота и фактическом бронировании; timezone филиала; атомарный lock + идемпотентность. Выход: 100+ конкурентных запросов на последний слот/зал дают не более одного разрешённого занятия на вместимость; архив сотрудников не стирает завершённые визиты.

**09 — Законченная студия танцев как первый эталон (P0).** Москва: 2 филиала, 12 направлений, минимум 52 тренера включая двух работающих совладельцев, 2 менеджера 2/2, 3 зала в А (1 групповой и 2 субаренда), своя аренда 700 тыс./мес в А. Группы, расписание серий занятий, неявки, списание/заморозка/перенос абонементов; разовое 2400 ₽, 10 посещений 7000 ₽, индивидуальное 3500 ₽, отдельная выручка субаренды. Фонд зарплат/ставки/оклады, договоры аренды с графиком платежей, задолженность/семья/личный кабинет. Не выдумывать вторую аренду, налоги, взносы, ФОТ и стоимость сдачи залов. Выход: месяц операций и закрытие на реальной DB, два филиала и роли; 700 ₽ — цена использованного посещения по пакету, 7000 ₽ оплаты не означает признанную выручку за 10 занятий.

**10 — Заказы, каталог, закупки, склад и OMS (P0 для торговли).** Общий SKU, варианты, категорийность, цены по филиалам/клиентам, себестоимость, заказ покупателя → резерв → закупка/приёмка → отгрузка/выдача → возврат; WMS адрес/скан и владелец товара для 3PL. На уровне МойСклад разделять заказ, резерв и физическое изменение запасов; они не тождественны. Выход: двойная продажа последнего SKU невозможна, склад/OMS/WMS/финансы сверяются; частичная отгрузка и частичный возврат корректны.

**11 — POS, эквайринг, онлайн-оплата, ККТ/ОФД (P0 для торговли и приёма денег).** Узкая роль кассира, смены, кассовые операции, подтверждение/отказ/возврат платежа, фискализация в применимых по РФ ситуациях, статусы платежа и чека независимо, корректные предоплаты/зачёты и чек возврата; реальные provider reconcile и адаптеры для поддерживаемых устройств. Для маркированных товаров включать отраслевую обязательную проверку, не заявляя автоматическое покрытие всех групп. Выход: полный sandbox PSP+ККТ, нет двойного списания/чека, проверены 54-ФЗ и правила применимого режима с бухгалтером/экспертом.

**12 — Деньги, расходы, зарплаты, налоги, достоверная прибыль (P0).** Единый cash/bank/obligations ledger, P&L/ДДС/дебиторка, план-факт, аренда помещений как расходы, сдача помещений как отдельный доход, зарплата по правилам, налоги/взносы как отдельные обязательства, закрытие периода, предотвращение задвоений. Доход, оплата и будущая услуга различаются. Для бухгалтерской и налоговой отчётности обеспечить проверенный маршрут через уполномоченного оператора, бухгалтерский экспорт или аттестованный модуль; не обещать автоматическую сдачу в ФНС без реальной интеграции, юридических прав и эталонной сверки. Выход: сверка с внешним эталоном, до копейки по выручке, платежам, обязательствам и зарплате по выбранным кейсам, нет выдуманной прибыли при неполной себестоимости.

### Этап C. Клиент и интеграции (спринты 13–16)

**13 — Интеграции и обработка сбоев (P0 по реально продаваемым возможностям).** PSP/SBP, банк, ККТ/ОФД, email/уведомления, сайт/онлайн-запись; для торговых ниш — доставки/маркетплейсы, для склада — WMS/скан/3PL. Секреты в безопасном хранилище, токены и правовой consent, события входа/выхода, retry, DLQ, мониторинг запаздывания и повторная сверка. Отсутствующий провайдер явно помечен «не поддерживается», а не «подключён». Выход: для каждого заявленного адаптера сертифицированный sandbox набор ошибок 401/403/429/503/timeout/duplicate webhook, без повторных денег и накладных.

**14 — Кабинеты клиента и сотрудника, уведомления (P0 для услуг, P1 для иных ниш).** Клиент/родитель видит только свои группы, посещения, тренеров, действующие и истёкшие пакеты, подтвердившиеся оплаты и задолженности, доступные отмены/переносы; возможны вход, восстановление и отзыв доступа. Тренер видит только свой график/явку/правомерно видимую зарплату; менеджер — рабочий журнал, но не банковские счета. Email/SMS-провайдеры и сообщения только при законном основании/согласии, очередь ошибок. Выход: семья A никогда не видит семью B; отзыв доступа действует на открытой сессии, никакой ложной оплаты в кабинете.

**15 — Управленческая аналитика и контроль целостности (P0).** По компании, юрлицу, филиалу, услугам/категориям, сотрудникам, группе, клиентскому сегменту и периоду: выручка vs поступления, задолженность, расходы, зарплаты, маржа, загрузка залов, аренда, сезонность; для торговли — оборачиваемость/возвраты/закупки, для агентства — проектная себестоимость. Показать источник каждого числа и свежесть данных, статус «недостаточно исходных данных» вместо подставленного 0. Выход: dashboard сходится с первичными документами/ledger, доступ к финансовой аналитике соблюдает RBAC.

**16 — Импорт, миграция, обучение, поддержка и прекращение подписки (P0).** Сценарии из YCLIENTS/МойСклад/CSV-XLSX, preview, поля/ошибки/дедупликация, идемпотентность, контрольные суммы, возможность временного параллельного ведения. Помощь прямо в интерфейсе, обращения/статусы, история операций, экспорт собственных данных и безопасное удаление/хранение по политике. Выход: новый клиент переносит данные без дублей, прекращение доступа не уничтожает его информацию и нет vendor lock-in без экспорта.

### Этап D. Доказательство коммерческой готовности (спринты 17–21)

**17 — Эксплуатация, обновления и восстановление (P0).** Мониторинг API/Postgres/Redis/outbox/платежей, уведомления об инцидентах, резервирование, реальные backup→restore, миграционные preflight, откат приложения без отката успешно проведённых финансовых операций, защита от noisy neighbor. Подтвердить RPO ≤15 мин и RTO ≤60 мин как **цели**, не как текущие гарантии; SLO 99,9% измерять только после испытаний. Выход: документированная проверка аварийного восстановления и развёртывания на staging.

**18 — Интеграционная и многоролeвая приёмка (P0).** Детерминированные сценарии на disposable БД: владелец→менеджер→сотрудник→клиент→бухгалтер→склад; минимум 2 tenant, 2 филиала, 52 тренера, конкурентные услуги и резервы, RLS, PSP/ККТ sandbox, billing, налоги в разрешённой модели, возвраты, архив и повторный вход. Устранить конфликт общего gate с ограничением 5 регистраций/IP/ч за счёт отдельных изолированных окружений/тестовых fixtures, не отключать лимиты. Выход: 100% обязательных golden E2E без BLOCKED; 0 известных P0; подтверждённый build/test/replay/restore/performance.

**19 — Аттестация всех отраслей, заявленных для продажи (P0).** 17 vertical codes ≠ 17 готовых бизнесов. Для каждой отрасли запуск с нуля по 8 общим + 5+ специализированным экранам, реальная позитивная и негативная операция, свой лимит/роль/бухгалтерия/платежи/загрузка. Принять «SUPPORTED», «PILOT» или «UNAVAILABLE» по доказательствам. Не продавать как полноценный WMS/автосервис/маркетплейс профиль без завершённого собственного цикла. Выход: матрица готовности 17×(onboarding, операция, деньги, роль, возврат, аналитика, поддержка), каждый рекламируемый профиль полностью ACCEPTED.

**20 — Закрытый пилот и исправление фактических дефектов (P0).** 5–10 реальных компаний в поддерживаемых нишах, включая крупную студию и торговлю. Две недели минимум реальных ежедневных операций с поддержкой (рекомендация, не доказанная оценка срока), сбор тикетов, инцидентов, затруднений onboarding; выплат/фискализации только по законному маршруту. Не прекращать пилот при непроверенном месячном закрытии там, где это обязательный сценарий. Выход: ни одного открытого P0; проверенные отчёты, поддержка и миграция; письменное решение GO/NO-GO владельца.

**21 — Коммерческий запуск и сопровождение (P0).** Публичные тарифы/договор/оферта/политика персональных данных, правила возвратов и хранения, информация о провайдерах, самообслуживание: оплатить/продлить/сменить/отменить/выгрузить, инцидент-центр, версионирование, статус возможностей каждой ниши. Запуск ограниченного круга и последовательное увеличение нагрузки по метрикам. Выход: пользователь платит, самостоятельно начинает бизнес, на следующий день продолжает с теми же данными, получает помощь и может безопасно уйти из сервиса.

## Поэтапное коммерческое открытие

- **Gate A — внутренний релиз-кандидат:** PASS 01–05, 17–18 и обязательной части 12; ничего не продавать, пока оплаченный тариф не проходит внешнюю сверку.
- **Gate B — платный пилот студий/сервисов:** дополнительно PASS 06–09, 11–16 (по применимым интеграциям), завершена месячная модель студии, серверное семейное разграничение и клиентский портал, QA и явные ограничения.
- **Gate C — торговые клиенты:** дополнительно PASS 10–11, соответствующие 13/15/19: последнее SKU, магазин + касса, возврат, склад, чек, доставка.
- **Gate D — общий коммерческий запуск:** все обязательные 01–21, проданные отрасли из 19 имеют ACCEPTED.

Нельзя называть продукт «готов для всех 17 отраслей» только потому, что их можно выбрать в меню.

## Go/No-Go: измеримые обязательные критерии

- Успешная полная установка и обновление БД, сборка из чистой копии, без фатальных тестовых ошибок.
- Производственная БД использует отдельную непривилегированную роль; ни один тест чужого tenant/детей/финансов не прошёл ошибочно.
- Положительные/отрицательные случаи для каждого заявленного отраслевого процесса и каждой роли, включая повторные запросы.
- Касса/PSP/биллинг: ноль неподтверждённых транзакций, ошибочно отмеченных PAID/REFUNDED/FISCALIZED, никаких дублирующих необратимых операций.
- Финансовые отчёты воспроизводятся по исходным документам; неизвестные расходы/налоги показываются как отсутствующие.
- Подтверждённые нагрузочные метрики, отдельная проверка noisy-neighbor, восстановление backup с проверкой данных.
- Подтверждённая оператором/бухгалтером правовая корректность платёжно-фискального и регламентированного контура для заявленного применения.
- Пользователь без инженера самостоятельно регистрируется, платит, создаёт компанию, настраивает профиль и совершает реальную операцию; может исправить ошибку.
- Пилот не имеет критических дефектов и имеет владельца каждой оставшейся задачи; решение GO зафиксировано для конкретного релиза.
- У каждого рекламируемого vertical profile есть отдельная доказанная приёмка. Не прошёл → статус PILOT/UNAVAILABLE и отсутствие коммерческих обещаний.
