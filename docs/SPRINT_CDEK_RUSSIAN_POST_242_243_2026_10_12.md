# CoreBiz — СДЭК и Почта России, дополнительная реализация (12.10.2026)

Исходники в `main`, без GitHub Actions. **Production GO не выдан.**
Публичный checkout не предлагает и не включает в оплату динамические тарифы
перевозчиков. Это отдельная задача, которую нельзя скрывать за статусом
`VERIFIED` API-ключа.

## Что добавлено

### Почта России

- Миграция `242_russian_post_shipment_claims.sql`: отдельная таблица
  tenant/site/order/quote с RLS, уникальным заказом, фиксированным
  digest параметров, режимами `SENDING/UNKNOWN/BACKLOG/REVIEW_REQUIRED`.
- Фиксированный `PUT https://otpravka-api.pochta.ru/1.0/user/backlog`
  c ключами продавца в HTTP-заголовках. Верифицируется только
  `result-ids[0]`; 200 с массивом ошибок не считается успехом.
- Правила отправки: существует сохранённый тариф с непросроченными
  15 минутами и неизменными реквизитами, индекс и вес точны;
  один реальный магазин, подтверждённая YooKassa-оплата и Finance,
  фискальный чек, складской резерв, адрес из оплаченного заказа.
  Используется существующий режим `LOCAL_COURIER`: стоимость от
  перевозчика оплачивается продавцом, покупателю не доначисляется.
- Запись заявки фиксируется **до внешнего PUT**. Таймаут/неопределённый
  HTTP-ответ → `UNKNOWN`; автоматически повторять PUT **нельзя**.
- `GET /1.0/backlog/{id}` и
  `GET /1.0/backlog/search?query=<orderUUID>` используются исключительно
  для read-only сверки с собственным UUID CoreBiz. Проверяется совпадение.
- UI `/app/settings/integrations/post`: оператор оформляет заказ
  из свежего тарифа и сверяет статус; секреты не возвращаются в браузер.
- Тесты: API endpoint/method/auth, ошибки даже при HTTP 200,
  точная привязка заказа, запрет повторной отправки и замены адреса.

API (роль `sites.manage=all`):
- `GET /api/v1/provider-connectors/sites/:siteId/russian-post/shipments`
- `POST /api/v1/provider-connectors/sites/:siteId/russian-post/shipments`
- `POST /api/v1/provider-connectors/sites/:siteId/russian-post/shipments/:shipmentId/reconcile`

### СДЭК

- Миграция `243_cdek_final_shipping_states.sql` не позволяет спутать
  `NOT_DELIVERED` («Не вручено») с `IN_TRANSIT` («В пути»), отдельно
  учитывает `REMOVED` («Удалён перевозчиком»).
- Проверка статуса не откатывает терминальное состояние при
  запоздавшем API-ответе, не теряет прежний трек-номер и возвращает
  фактически записанное состояние. Доставка не проводит финансовую
  оплату или списание складских остатков автоматически.
- Quote связан с текущими зашифрованными реквизитами продавца;
  старый quote после смены ключей нельзя использовать.

## Что пока не реализовано

**СДЭК:** выбор пункта выдачи/тарифа и точной цены до оплаты
покупателем, выдача PDF ярлыка/ШК, отмена, возвратная логистика,
автоматические подтверждённые события и сверка API в sandbox.

**Почта России:** формирование и передача партий, юридически значимая
передача посылки в отделение, генерация ШПИ и PDF этикеток,
достоверный трекинг движения/вручения из внешнего источника, отмена
и возврат. Статус `BACKLOG` — запись в «Новых», **не отгрузка**.

**Общее:** чек полного расчёта после предоплаты, независимая
сверка с банком/ОФД/складом, сценарии отмены/возврата,
параллельные заказы последнего SKU, P95/P99 мониторинг.
`99,99%` пока не измерено и не гарантировано.

## Обязательная проверка до активации на сервере

1. Сделать и восстановить резервную копию БД на одноразовом стенде.
2. Применить миграции **в порядке** до `243`, в частности
   `241` → `242` → `243`. Не применять вручную без штатного
   migration runner и его журнала.
3. Запустить без CI: `pnpm typecheck && pnpm test && pnpm build`,
   `pnpm stability:check`, `node scripts/migration-preflight.mjs`.
4. В отдельной тестовой компании проверить конкурентный booking,
   истёкший quote, смену ключа, чужой tenant, отсутствие фискального
   чека, пустой адрес, HTTP 200 с ошибкой и timeout после создания.
5. Сверить `result-ids` в реальном кабинете Почты России, отдельно
   проверить структуру обязательных адресных полей для договора.
6. Для СДЭК использовать тестовый договор и доказать реальные
   `NOT_DELIVERED/REMOVED` и последовательную историю, не только
   замоканные ответы.
7. Не включать почтовое оформление для клиентов до подтверждения
   провайдером payload, договором и эксплуатационной приёмкой.
