## Ролевая матрица HTTP-приёмки

| Роль | Разрешённый бизнес-сценарий | Обязательный запрет |
|---|---|---|
| OWNER | Управление компанией, сотрудниками, ролями, CRM, финансами, складами | Запрещено «назначить OWNER» не-владельцу через роль |
| ADMIN | Управление командой и ролями в пределах выданных прав | Самоназначение OWNER, чужой tenant, делегирование выше себя |
| SALES_HEAD | Общая воронка команды | Финансы без finance.read |
| SALES_MANAGER | Создать свою сделку, видеть её и собственные задачи | Сделка владельца и другого менеджера при scope=own |
| PROCUREMENT | Просмотр каталога и складов, закупочный процесс | Платежи и проводки без finance.write |
| WAREHOUSE | Просмотр остатков и проведение складского движения | Банковские счета и финансовые сводки |
| FINANCE | Просмотр и проводки финансовых операций | Изменение складских остатков и ролей |
| SERVICE_STAFF | Собственные записи, обслуживание клиентов | Чужие визиты и финансовые суммы без finance.read |
| VIEWER | Только чтение разрешённых разделов | Изменение SKU, запасов, платежей или пользователей |

Все роли нужно дополнительно проверить при отключении capability, истечении
сессии, повторном входе, смене филиала, нескольких ролях одновременно,
другом tenant, отключении пользователя и блокировке подписки.

## Реальный многоролевой HTTP-сценарий добавлен в проект

`scripts/multirole-api-e2e.mjs` на *новом disposable окружении*:

1. Проверка API и запретов для гостя (401).
2. Регистрация OWNER и создание тестовой компании.
3. Создание товара, склада, услуги и сделки.
4. Приглашение двух пользователей через реальные одноразовые ссылки.
5. Работа первого сотрудника: VIEWER → SALES_MANAGER → SALES_HEAD →
   PROCUREMENT → WAREHOUSE → FINANCE → SERVICE_STAFF → ADMIN → VIEWER.
   Каждый переход делается владельцем через `PUT /roles/assign`, затем
   немедленно проверяется действующая сессия `GET /workspace/context`.
6. Позитивные проверки: складской оператор проводит движение; финансист
   создаёт счёт; менеджер ведёт собственную сделку; руководитель видит
   воронку команды; мастер читает разрешённый журнал.
7. Негативные проверки: запрещённые API возвращают 403, чужая CRM-сделка
   не попадает в own-воронку, ADMIN не становится OWNER.
8. Вторая компания: сотрудник первой не переключается в чужой tenant,
   не читает чужую сделку и не может получить роли чужой компании.
9. Демотирование к VIEWER отзывает прежние привилегии.
10. Logout закрывает доступ в той же сессии.

Только 3 регистрации, а не 9: тест учитывает лимит 5/час/IP, не
обходит или не отключает защиту. Тестовые пароли/токены не выводятся
в отчёты и логи.

## Выявленные пробелы — НЕ PASS

**P0/P1: отдельный кассир отсутствует.** В миграциях есть FINANCE,
но нет роли `CASHIER`. POS открывает/закрывает смену под `finance.write`,
которое также требуется для значительной части финансовых операций.
Нужно спроектировать узкие разрешения кассовой роли (`retail.shift.manage`,
`retail.sale.manage`, `retail.refund.manage`) и проверить миграции/авторизацию,
а не давать кассиру весь FINANCE.

**P1: бухгалтер и кассир сейчас не являются отдельными полноценными
системными ролями.** Финансовая роль `FINANCE` не заменяет специальные
права к налоговым документам, закрытию кассы и зарплатам.

**P1: общий production-gate + rate limiting.** Несколько отдельных
e2e-сценариев последовательно регистрируют тестовых пользователей
с одного локального IP, и совокупно могут превысить пять регистраций
за один час. Чтобы реально запускать полный gate, каждому E2E-прогону
нужны собственные *изолированные Redis и API/БД*, либо безопасное
повторное использование специально созданных disposable пользователей.
**Нельзя отключать регистрацию/rate limit на production ради тестов.**
Падение на HTTP 429 — не успешное прохождение тестов ролей.

**P0: доказательство runtime не получено.** Нет живых данных:
параллельных REST запросов, RLS отрицательных попыток,
API доступа после отзыва membership, старых сессий, мобильной браузерной
симуляции, проверки собственных и командных филиалов.

## Команды на отдельном disposable окружении

```bash
git checkout main && git pull --ff-only origin main
pnpm test:roles
```

Для живых тестов **только после проверки**, что API использует
одноразовую PostgreSQL и отдельный тестовый Redis:

```bash
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_BASE_URL=http://127.0.0.1:4000 \
COREBIZ_SMOKE_WEB_ORIGIN=http://localhost:3000 \
pnpm test:roles:e2e
```

Сценарий создаёт компании, пользователей, сделки, услуги,
складские движения и финансовые счета. **Не выполнять на production.**
