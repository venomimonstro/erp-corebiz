# CoreBiz — зрелые процессы YCLIENTS и МойСклад, 13.10.2026

Цель: общая модель клиента, бронирования, услуг, склада, обязательств, зарплаты, платежей и финансов, без копирования чужого кода.

## Практики из документации

- [YCLIENTS, онлайн-запись по абонементу](https://support.yclients.ru/660): запись зависит от права посещения; отдельны бронирование, подтверждение оплаты и расход посещения. В CoreBiz это должно проверяться на сервере, не только формой.
- [МойСклад, складские остатки/резервы/ожидания](https://support.moysklad.ru/hc/ru/): доступность = остаток + ожидание − резерв. Складские движения требуют документов, а не произвольного изменения остатка.
- [МойСклад, прибыльность](https://support.moysklad.ru/hc/ru/): разделять продажи, себестоимость, возвраты, зарплату и маржинальность, не подменять прибыль оборотом.

## Сквозная логика студии танцев

Регистрация → два филиала → 3 зала в первом (один групповой, два для субаренды) → 12 направлений → 52 тренера → 2 менеджера 2/2 → услуги/индивидуальные цены → группа → урок → родитель и ученик → абонемент → резерв права посещения → явка → списание посещения → начисление тренеру → финансовое обязательство → подтверждённый платёж → отчёт владельца.

Известны 3 млн ₽ планового оборота, 700 тыс ₽ аренды залов первого филиала, 100 тыс ₽ двух окладов, 2400 ₽ разовое групповое занятие, 7000 ₽ абонемент из 10 занятий (700 ₽ условная цена использованного занятия), 3500 ₽ индивидуальное занятие. Аренда второго филиала, реальный ФОТ, налоги и прочие затраты **неизвестны**. Нельзя объявлять остаток после известных расходов чистой прибылью.

## Проверяемые инварианты

1. Изменение прайса не переписывает цену уже проданной услуги.
2. Если действующая программа ссылается на услугу, архивирование запрещено. Миграция **153** добавила `dance_program.service_id`; только проверка 151 была недостаточной. Исправлено в `BookingService.archiveService`.
3. Будущие бронирования блокируют архивирование услуги/ресурса; история занятий сохраняется.
4. Родитель видит только детей по разрешённой связи и собственные оплаты; роль `DANCE_CUSTOMER` не получает CRM и финансы всей студии.
5. `DANCE_MANAGER` ведёт расписание, абонементы и долги без полномочий на банковские счета и payroll.
6. Неподтверждённый финансовый статус — UNKNOWN, а не «оплачено 0 ₽».
7. Расход аренды из договора нельзя одновременно полностью учитывать дважды через себестоимость каждого урока.
8. Резерв товара, отгрузка, возврат, списание расходников и повторный webhook должны быть идемпотентны.
