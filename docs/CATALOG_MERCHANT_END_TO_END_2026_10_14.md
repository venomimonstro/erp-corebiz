# CoreBiz: каталог, массовый импорт и складской товарооборот
Редакция 14.10.2026. Ветка: main. Статус: внесено в исходники, production GO **не подтверждён**.

## Цель
Владелец интернет-магазина, розницы, опта и студии танцев с магазином
работает с **одними сущностями**: `product → product_variant → sku →
purchase_order → goods_receipt → inventory_balance → sales_order`.
Никакого «второго каталога для e-commerce» не создаётся.

## Этап 1. Добавить товар
Экран `/app/catalog/products` → «Новый товар»:
название, STOCKABLE/NON_STOCK, SKU (автоматически если пусто),
штрихкод, категория, описание, цена продажи, закупочная цена при
финансовых правах, фото HTTPS и до 40 пар характеристика-значение.
Сохранить → карточка появляется в каталоге, но количество на складе **0**,
поскольку товара физически ещё не приняли.

Ошибки: SKU уже используется, некорректная цена или атрибут, неподходящая
ссылка на изображение, чужая категория — операция отвергается сервером
до частичной записи; транзакция не должна оставлять полутовар.

## Этап 2. Изменить или архивировать
Найти товар по названию, SKU или штрихкоду, открыть карточку:
- менять название, категорию, описание, характеристики и фото;
- менять цену продажи, закупочную только с правом finance.read /
  catalog.cost.read / wildcard;
- отдельно смотреть складские физические остатки, резервы и доступное
  количество по каждому складу;
- архивировать, только если нет физического остатка, резерва,
  незавершённых клиентских заказов и закупок.
Архивация атомарно закрывает product/variant/sku. История документов
сохраняется, активные заказы не теряют SKU.

**Ограничение:** прямой upload двоичных фото на собственное хранилище
ещё не выполнен. Фото вводится HTTPS-ссылкой. Нужен отдельный сервис
медиа с антивирусом/проверкой MIME, ограничением разрешения,
S3-совместимым хранилищем и квотами по tenant.

## Этап 3. Массовая загрузка Excel/CSV
`/app/migration` → тип PRODUCTS → скачать
`/templates/catalog-products.csv` → выбрать файл до 10 MB →
проверка и предпросмотр → подтверждение операции.
Распознаются русские и английские заголовки:
Название, Артикул, Штрихкод, Цена, Закупочная цена, Категория,
Описание, Фото, Тип товара и `Характеристика: <имя>`.
XLSX уже обрабатывается ExcelJS; CSV поддерживает UTF-8, UTF-16LE,
Windows-1251, разделитель ; / , / TAB и кавычки.

Правила:
- Без SKU создаётся **стабильный** AUTO-код по названию: повтор файла
  не создаёт произвольные новые артикулы.
- Повтор SKU или штрихкода в одном файле показывается ошибкой
  **до** импорта; ошибки не уничтожают корректные строки.
- Владелец выбирает «существующие SKU пропускать» или **явно**
  «обновить существующие», включая ранее пропущенные в данном batch.
- При обновлении пустые ячейки цены, фото, штрихкода, описания или
  характеристики НЕ стирают существующие данные.
- Закупочная цена в импорте также требует финансовых прав.
- Статусы VALID/ERROR/IMPORTED/SKIPPED + повтор того же batch
  не должны создавать вторые товары.
- Импорт **не** пишет непосредственно в inventory_balance и
  не притворяется реальным складским приходом.

**Ограничение:** ручной маппинг произвольных колонок, загрузка
изображений с компьютера, фоновая обработка сотен тысяч строк
и многоуровневый процесс сложных наборов модификаций ещё требуют
отдельного спринта. В текущем CSV каждая строка — свой SKU; атрибуты
основной модификации уже записываются в существующую JSONB-модель.

## Этап 4. Закупка и фактический приход
`/app/purchases`:
1. Создать поставщика.
2. Выбрать SKU, количество, цену закупки, конкретный склад назначения
   и ожидаемую дату.
3. Создать заказ поставщику. **Остаток не меняется.**
4. Подтвердить заказ.
5. После получения товара выбрать «Принять товар», ввести реальное
   количество, отметить подтверждение.
6. Только `POST /procurement/orders/:id/receipts` создаёт
   документ прихода и изменения authoritative складского ledger.
7. Повтор после потери ответа использует тот же idempotencyKey
   и fingerprint; ключ сохраняется в sessionStorage в рамках сеанса.
8. `/app/inventory/stock` показывает факт/резервы/доступный остаток.

## Самотест
- Структурная проверка GitHub исходников: **13/13** проверок —
  наличие API, цены/права, ошибки CSV, категории, атрибуты, статусы,
  закупки, архивирование.
- Jest `catalog-merchant-operations.spec.ts` добавлен для:
  маскирования себестоимости, запрета несанкционированных изменений,
  запрета архивации с остатком и атомарного архивирования.
- `node --test scripts/catalog-merchant-contract.test.mjs` —
  статические регрессии.
- `scripts/catalog-product-owner-e2e.mjs` — **реальный мутирующий**
  сценарий на одноразовой PostgreSQL: создание → редактирование →
  CSV update → повтор batch → закупка → подтверждение → реальный приход
  → повтор того же ключа → отрицательный тест архивирования с остатком.

**Важно:** источник и наличие тестов проверены, а полная сборка
pnpm typecheck / Jest / браузер / реальные DB-транзакции **не
выполнены в этой сессии**. Запускаться должны строго на
disposable API/DB/Redis. Никаких заявлений о готовности коммерческого
релиза до прохождения всех P0 проверок.

## Команды
```bash
git checkout main && git pull --ff-only origin main
pnpm test:catalog
pnpm typecheck && pnpm test && pnpm build
```

Далее только на отдельном localhost API и одноразовой DB:
```bash
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_BASE_URL=http://127.0.0.1:4000 \
COREBIZ_SMOKE_WEB_ORIGIN=http://localhost:3000 \
pnpm test:catalog:e2e
```

## Следующая очередь
P0: обязательное runtime тестирование API и исправление найденных
несоответствий, проверки tenant RLS, параллельные заказы последнего SKU,
мобильная симуляция владельца.
P1: полноценная медиабиблиотека; редактор вариантов размеры/цвета
с индивидуальными фото, ценами и остатками; категорийное дерево,
массовая правка, история изменения цены, ручное сопоставление колонок
и экспорт по ролям.
P2: прайс-листы поставщиков, интеграция 1С/МойСклад/маркетплейсов,
синхронизация фото и данных через планировщик, alert на критические
остатки и ABC/XYZ анализ.

Сравнивали принципы с официальной документацией МойСклад:
