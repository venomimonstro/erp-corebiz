# CoreBiz — аудит первого рабочего дня в 16 нишах

Дата: 2026-10-11. Ветка: `main`. Без CI / GitHub Actions.

## Методика и достоверность

Выполнен аудит реального исходного кода регистрации, отраслевых шаблонов,
capability/permission guards, главного экрана, активирующих шагов, профильных
UI страниц и существующих API. По обнаруженным отклонениям внесены
изменения в frontend/backend и регрессионные тесты.

**Это аудит исходников, НЕ результат реальной браузерной симуляции.**
Миграции на PostgreSQL, E2E с реальными работниками/покупателями,
платежи PSP, фискальные чеки, начисление зарплаты и налоговая
отчётность в этом сеансе не запускались. Статус реализации в таблице
означает «API/UI обнаружены в исходниках», а не «принято как PASS».

## Регистрация и первый вход

1. На `/signup` клиент выбирает сферу из **16 существующих** ниш.
   Выбор обязателен, случайный пресет танцев исключён.
2. `POST /auth/register` регистрирует владельца и изолированную
   компанию с сессией. Затем `PUT /customization/business-vertical`
   атомарно включает профиль, права видимости модулей, поля и метаданные.
   Если настройка отрасли не завершилась, аккаунт **не потерян**:
   маршрут `/app/start?vertical=...` позволяет повторить шаг.
3. `/app/start` — простой план первого запуска: вид бизнеса,
   реальные операционные потоки, кнопка «Применить», список шагов,
   отметки на основе данных DB, ссылка прямо в профильную страницу.
4. Меню автоматически ограничивается актуальными разделами выбранной
   ниши, а ручной вариант навигации запоминается **отдельно для
   каждой компании**, а не глобально для браузера.
5. На `/app` главный экран владельца предлагает прямую кнопку
   «Открыть студию / магазин / автосервис / проекты / склад».

Смена вертикали НЕ удаляет бизнес-документы; скрытые модули доступны
вновь после включения. Метрики прохождения старого вида бизнеса не
выдаются за успешный запуск нового.

## Конкретные найденные и устранённые ошибки

- **P0: случайный универсальный кабинет после регистрации.** Добавлен
  выбор ниши на регистрации и отдельный первый день.
- **P0: студия не может создать направление без услуги**, однако
  мастер-чек-лист пропускал это условие. В `/dance/readiness`,
  `/dance/dashboard`, `/dashboard/activation` добавлено создание
  услуги ДО направления; добавлен первый ученик.
- **P0: автосервис терял клиента при вводе автомобиля из UI.**
  `automotive.createVehicle` поддерживал `partyId`, но форма
  его не отправляла. Добавлен выбор существующего клиента.
- **P1: разные ниши имели один generic SERVICE onboarding.**
  Танцы, салоны, авто и агентства теперь используют разные
  действительные таблицы для выполненности этапов.
- **P1: розница, опт и маркетплейс проходили одни и те же шаги.**
  Теперь проверяются соответственно остатки/продажи,
  коммерческие условия клиента и действительно
  импортированный заказ из канала.
- **P1: WMS READY ошибочно означало первую ценность.** Теперь
  first-value наступает только после `wms_task.status='DONE'`.
- **P1: смена vertical сохраняла старый completed milestone**,
  создавая ложное впечатление успешного запуска. Смена ниши
  сбрасывает checkpoint новой адаптации без удаления бизнес-данных.
- **P1: меню другого арендатора наследовалось из localStorage.**
  Настройки навигации стали tenant-scoped.
- **P1: API принимало Boolean('false') как true**, включало
  неожиданный модуль или скрывало onboarding. Теперь API
  требует настоящий JSON boolean; нестроковые названия ниши
  отклоняются до SQL.

## Что остаётся открытым и блокирует честное обещание «всё работает»

1. Во **всех 16 вертикалях** нет фактического PASS на пути
   «регистрация → первая операция → долг/оплата → отчёт» с
   чистой PostgreSQL и двумя тенантами. Тесты в репозитории
   проверяют отдельные функции и guard, но не заменяют полный
   Playwright/API journey.
2. Подтверждение полноценной **налоговой отчётности РФ,
   чеков ККТ и выплат зарплаты** требует отдельных интеграционных
   сценариев и правовой проверки. Нельзя показывать зелёный статус
   «ФНС отправлено», пока шлюз не подтвердил приём.
3. Для танцев нужны lifecycle-тесты **пробное → абонемент →
   посещение/отработка → начисление тренеру → оплата/возврат →
   отчёт по залу**, включая конкурирующую запись и повторные
   вызовы по idempotency key.
4. Для красоты/маникюра нужны **мастер + рабочее место +
   длительность + материалы + payroll** без двойных бронирований.
5. Для авто нужны end-to-end **VIN → согласованные работы →
   запчасти из ledger → выдача/акт → оплата → возврат**.
6. Для торговли нужны **запасы/резерв/продажа/возврат/доставка/
   эквайринг/ККТ/проверка банка**.
7. Для маркетплейсов — настоящие **Ozon/WB staging API**
   с фоновыми очередями, комиссией и ошибками поставщика.
8. Для 3PL — **ASN, размещение, отбор, owner isolation, SLA,
   счёт хранения и tenant reconciliation** на concurrent нагрузке.
9. Отраслевые dashboards не должны обещать реальную прибыль
   без учтённых налогов, банковских комиссий, возвратов и зарплат.
10. Восстановление пароля и подтверждение email остаются
    отдельными проблемами реального customer onboarding.

## Коммерческие критерии приёмки

- Пользователь каждой ниши выбирает профиль за регистрацию и
  получает первые задачи без инструкций в отдельном PDF.
- Каждая кнопка ведёт на существующий маршрут с реальным
  разрешённым backend-оператором.
- Шаг «выполнено» подтверждён данным конкретной ниши, не
  чужой записью и не кликом.
- Переключение компании/профиля не раскрывает чужие данные и
  не удаляет ранее созданные документы.
- Роли сотрудников видят только разрешённые им графики,
  клиентов, долги, зарплаты и прибыль.
- Выплаты и PSP/банк отражаются в едином ledger строго один раз.
- `pnpm typecheck`, `pnpm test`, `pnpm build`,
  миграции, staging E2E, восстановление и конкуренция — PASS.
- До этого **NO-GO для массовой продажи как полностью
  закрывающего все процессы вертикального ERP**.

Команда локальной проверки без CI (не запускать mutation smoke на production):

```bash
git checkout main && git pull --ff-only origin main
corepack enable && pnpm install --frozen-lockfile
pnpm typecheck && pnpm test && pnpm build && pnpm stability:check
```

Далее провести отдельные E2E бизнес-путешествия на staging, сохранив
отчёт с идентификаторами tenant, заказов и фактом ledger reconciliation
без платёжных секретов и персональных данных.
