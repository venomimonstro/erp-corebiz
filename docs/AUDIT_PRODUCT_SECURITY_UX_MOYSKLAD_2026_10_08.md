# ERP CoreBiz — технический, продуктовый и конкурентный аудит
Дата: 2026-10-08. Репозиторий: venomimonstro/erp-corebiz, ветка main.

## 0. Честные границы аудита
Изучены дерево репозитория, выборочные ключевые файлы NestJS, Next.js, PostgreSQL, worker, auth, finance/dashboard, WMS/OMS, документы и официальные материалы «МойСклад». **Это статический аудит кода и продуктовая gap-analysis**, не независимое подтверждение production качества. Не проводились: запуск PostgreSQL, replay всех миграций, load test, динамический pentest, просмотр интерфейса в реальном браузере и реальные платежные/фискальные операции. Интеграционные замечания имеют статус «требует проверки», если нет прямого доказательства в коде.

## 1. Executive decision
**Заморозить новые широкие модули до закрытия P0**; завершить три продаваемых end-to-end сценария, а не выпускать десятки «готовых» по названию модулей.

Сильные стороны: modular monolith; tenant context + декларативные RLS policies; складские леджеры и 3PL owner dimension; OMS/закупки/продажи/CRM; сервисные записи; transactional outbox; возможность адаптировать поля и формы; задел финансовых подсистем. Слабость: верификация, production DB права, неполная сквозная интеграция, устаревшая документация и неадаптированная навигация.

## 3. P1 — важное до первого платного клиента
- **Auth:** присутствуют login/register/logout/switch; в проверенном AuthController отсутствуют восстановление доступа, управление активными сессиями, step-up для денег/ролей, полноценная 2FA политика из docs/SECURITY.md. Определить безопасный onboarding и recovery.
- **Observability:** HTTP trace-id и часть метрик есть; нужны structured logs без персональных данных, DB lock/queue metrics, correlation_id от покупки до склада/денег, failed jobs DLQ, alerts.
- **Outbox:** убедиться в восстановлении PROCESSING после падения worker и idempotent повторе; отдельный сценарий crash-after-commit-before-ack.
- **Import:** rollback/preview, mapping, audit conflict log; импорт не должен создавать неявно финансовых остатков или дубли.
- **API:** DTO whitelist/schemas на публичных и финансовых POST; у некоторых контроллеров тип body = any. Нужны explicit validation, max sizes, guards, 429 по ключам/источникам.
- **Custom domain:** проверить tenant binding для Host/X-Forwarded-Host (trust proxy config и allowlist доменов), защита от host header poisoning.
- **Finance:** реальная выручка отдельно от заказов и денег; refunds/fees/marketplace commissions/acquiring, purchase costs, cashflow + accrual P&L.
- **Latency:** курсорная пагинация и индексы для истории заказов, складских задач и событий; не загружать 5000 строк на открытие страницы.
- **UX:** backend accounting/payroll/bank flows без полноценных клиентских рабочих экранов; глобальное меню содержит слишком много модулей, не отражает роль/отрасль.

| Возможность | CoreBiz по исходникам | Приоритет | Стратегия |

| Складские резервы, отгрузки, инвентаризация | Есть WMS/OMS ledger и задачи | P0 | Тесты гонок и сверка всех уровней остатков |
| Сквозная прибыль по заказу/каналу | Есть Growth и набросок dashboard | P0 | Комиссии, возвраты, доставка, реклама, себестоимость, признание выручки |

| Маркировка Честный ЗНАК и ЭДО | Не подтверждён промышленный контур | P1 в маркируемых категориях | Включать по отраслевому профилю; SKU GTIN/ТН ВЭД, код маркировки, статусы, проверки |
| Серии, партии, сроки годности, FEFO | Полное промышленное покрытие не подтверждено | P1 для опта/food/pharma | Lot/serial genealogy, FEFO, отзыв партий, уникальные идентификаторы |
| Техкарты, BOM, незавершёнка, производственные задания | Не подтвержден полноценный MRP | P1 только профиль Производство | Нормы материалов, маршрут, факт, отходы, калькуляция |
| Цены по контрагентам/оптовым прайсам | Нужна проверка сквозной работы | P1 B2B | Контрактные условия, объёмы, отсрочки, лимиты дебиторки |
| Онлайн-магазин, Ozon/WB, доставка | Есть sites, channel connectors, OMS | P0 для e-commerce | Заказ → резерв → отгрузка → маркетплейс-финансы → возврат |
| Бронирования ресурсов | Есть Service Ops bookings | P0 для сервиса | Абонементы, повторные визиты, no-show, загрузка мастеров |
| 3PL и владелец остатков | Есть WMS owner, 3PL billing и портал | P1 для 3PL | Owner-level сверка, SLA, корректировки счетов, owner-specific access |
| Роль и отрасль → простой интерфейс | SPEC есть; UI пока единое большое меню | P0 | Capability/role navigation, профили по виду бизнеса |

**Не пытаться догнать весь МойСклад за один релиз.** Критический дифференциатор CoreBiz — понятный owner cockpit + единый журнал денег/операций + отраслевые рабочие места.

## 5. Отраслевые профили
- **Интернет-магазин/маркетплейс:** товары, каналы, OMS/WMS, закупки, возвраты, прибыль на заказ; скрыть бухгалтерию и service bookings в первом дне.
- **B2B опт:** контрагенты, коммерческие предложения, оптовые цены, счета, кредитный лимит, дебиторка, склады/серии; скрыть кассу и запись клиентов.
- **Услуги/салон/школа:** график сотрудников и ресурсов, запись, пакеты/абонементы, предоплаты, услуги, задачи, касса; скрыть WMS/3PL.
- **Автосервис:** заказ-наряд, VIN/ТС, диагностика, нормо-часы, запчасти со склада, согласование сметы, гарантия.
- **Производство/кафе:** техкарты/BOM, задания, потребление материалов, партии, брак и себестоимость; включить лишь после надёжного учета складских движений.
- **3PL:** владелец товаров, контракты, SLA, inbound/ASN, тарифы и сверка начислений, клиентский портал.

Каждый профиль = конфигурация capabilities, labels, setup wizard, обязательных полей, шаблонов статусов и домашней панели; **не отдельная форкнутая кодовая база**.

## 6. UX: идеальная первая сессия
1. Выбор типа бизнеса и роли (владелец/оператор/закупщик/бухгалтер).
2. 3–5 важных настроек, всё остальное по умолчанию.
3. Импорт Excel/CSV/МойСклад или ручное создание одного товара/клиента/услуги.
4. Одно end-to-end действие за 5 минут: создать заказ, провести запись или оформить поступление.
5. Домашняя панель: «Сегодня», «Нужен мой ответ», «Где деньги», «Что сделать дальше».
6. Правильная ошибка с контекстом и действием, а не exception/trace.
7. Навигация не более 5–7 верхних пунктов на отраслевой профиль; скрытые блоки — через «Все модули».

Технически нужны серверная конфигурация по Capability/Role, поисковая строка Ctrl+K, глобальная кнопка «+ Создать», сохранение таблиц/фильтров, понятные пустые и ошибочные состояния, адаптивный mobile/TSД UX.

## 7. Интеграция и миграция из «МойСклад»
Считать JSON API 1.2 источником: metadata/entities/stock/reports/webhooks; учитывать пагинацию, лимиты/429, Retry-After, изоляцию клиентов, custom fields и внешние ID.

Рекомендуемый pipeline:
1. OAuth/token, секреты encrypted at rest и per-tenant isolation.
2. First-run dry-run: preview counts (товары/контрагенты/склады/документы) + сопоставление типов и статусов.
3. Создать `external_identity(tenant,source,object_type,external_id,internal_id,external_updated_at,checksum)`.
4. Импорт: категории → товары/варианты/SKU → контрагенты → склады → остатки **как начальные документы** → открытые заказы → платежи только как предварительные, под сверку.
5. Webhooks → deduplicated inbox → worker → per-entity reconciliation → alert on conflict.
6. Ночью reconciliation последних изменений, с учётом возможной потери webhook.
7. Не синхронизировать остатки «перезаписью поля»: у CoreBiz ledger как source of truth; использовать подтверждённые документы движения.
8. Показать пользователю таблицу ошибок импорта и кнопку безопасного повтора.

## 8. Измеримые release gates (вручную, без CI)
- Миграции 001–115 на чистой и реалистичной заполненной БД.
- **Под API DB role**, не суперпользователем, tenant A/B read/write/search/export denial.
- 100 конкурентных заказов на последний SKU: отсутствие отрицательного available и двойных отгрузок.
- WMS aggregate↔location↔owner ledger = 0 расхождений.
- Платёж 2×с тем же idempotency key — ровно одно списание.
- Импорт и webhook — at-least-once, duplicate-safe, out-of-order handling, retry/backoff.
- Восстановление после остановки DB/Redis/worker и из резервной копии.
- Browser E2E: регистрация → onboarding → заказ/запись → финансы → возврат; 3 профиля, мобильный экран.
- p95 API менее 500 ms, чтение dashboard менее 2s на типовых данных; сначала измерять, затем оптимизировать.
- Manual release report с доказательствами, владелец подписывает go/no-go.

## 9. Приоритет реализации
**Фаза А — безопасность/надёжность:** DB role/RLS, migrations, 20–30 критичных автотестов, CSRF/public API, webhook retries, backup restore, idempotency, API timeout.

**Фаза Б — продукт, который можно продать:** e-commerce/опт или услуги как первые 2 профиля; прибыль по факту; меню по роли; импорт МойСклад/Excel; полезный владелец dashboard.

**Фаза В — отраслевые глубины:** POS+ККТ/маркировка; B2B договоры/цены; production BOM; 3PL — только по подтверждённому спросу.

**Фаза Г — масштабирование:** performance measurements, queue SLAs, support diagnostics, mobile offline, disaster recovery, observability.

## 10. Исправления текущего аудиторского прохода
- Origin guard: подписанные публичные внешние POST маршруты отдельно от CSRF-защиты авторизованного API; тесты.
- Auth session: исключено необработанное отклонение асинхронного обновления last-seen.
- Dev Docker ports: loopback only.
- Sidebar: удалены ссылки на отсутствующие страницы.
- Public Next frontend: same-origin API rewrite и client URLs для публичных сайтов.
- Owner dashboard: без черновиков и смешанных валют; UI именует сумму заказов и оценочную маржу честно.
- Web API client: timeout/network/non-JSON error handling.
- SQL-диагностика производственных RLS прав.

### Ключевое решение
Нельзя честно объявить систему стабильной или «готовой к запуску» только по исходному коду. Приоритет — доказать целостность сквозных сценариев, а не наращивать счётчик спринтов.
