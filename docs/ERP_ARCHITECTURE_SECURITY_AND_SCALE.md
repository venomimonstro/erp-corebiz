# ERP CoreBiz — архитектура бизнес-процессов, безопасность и масштабирование

**Версия:** 2026-10-11 · **Статус:** проектные инварианты + аудит исходного кода. Не является сертификатом безопасности или подтверждением производительности.  
**Исходные компоненты:** NestJS API, PostgreSQL/RLS, Redis, фоновые worker-процессы, Next.js, outbox/domain events, отраслевые настройки, роли и permissions.  
**Где истина:** PostgreSQL фиксирует заказ, деньги, принадлежность организации и остаток; UI показывает проекции. Ни браузер, ни маркетплейс, ни AI-агент не могут сами изменить источник истины без авторизованной серверной команды.

## 1. Модульная модель и единые бизнес-объекты

| Ядро | За что отвечает | Иные модули взаимодействуют через |
|---|---|---|
| Tenants / Organization / Authorization | Организация, подразделения, пользователи, роли, права и границы видимости | TenantContext из проверенной сессии; серверные permissions и scope |
| Party / CRM / Tasks | Контрагент, плательщик, лид, сделка, следующий контакт, коммуникации | Party ID, Deal ID, Task ID; сохраняются tenant_id |
| Catalog | Единый SKU, вариации, артикулы, штрихкоды, цены, товары и услуги | SKU ID и service ID, без второго справочника у каждого канала |
| Sales / OMS | Заказ, позиции, способ исполнения, размещение резервов, отмены, отгрузка | SalesOrder ID → OMSOrder / allocations |
| Inventory / WMS / Procurement | Склад, физический приход, резерв, движение, партия, 3PL-владелец, приёмка, инвентаризация | Идемпотентный ledger и складские движения; ATP = физический запас − действующий резерв − страховой запас |
| Channels | WB, Ozon, Яндекс Маркет и прочие подключения; external offer → internal SKU | Order inbox → Sales/OMS, публикация запасов → channel_stock_target |
| Service Ops / Dance / Automotive | Запись в ресурсный календарь, исполнитель, зал/пост, посещаемость, техкарта/материалы | Услуга → бронь → факт → себестоимость и начисление |
| Projects / Agency | Проект, этапы, задачи, документы, согласования и договоры | CRM deal → project; deliverable → acceptance → invoice |
| Finance / Accounting / Payroll | Обязательства, счета, платежи, банковская сверка, выплаты, налоги и сроки | Типизированные source_type/source_id, immutable posting и audit |
| Analytics / Growth / Sites | Лид-источник, визит, заказ, рекламные расходы, сквозная маржа, публичные витрины | Корректное связывание channel/source и фактических заказов/платежей |
| Workflow / Worker / Notifications | Автоматизация и интеграции, асинхронные повторы, состояние jobs | Транзакционный outbox, idempotency keys, ограниченные retries |
| Operational Dashboard / Action Queue | Исключения и следующий полезный шаг владельца | Читает агрегаты и issue registry, не создаёт собственную бизнес-истину |

**Инвариант:** один контрагент — единый Party; один товар — единый SKU; один заказ — единый SalesOrder; резерв — в складском контуре; платёж — в Finance, не в отдельной Excel-подсистеме отрасли. При каждой связи `tenant_id` должен совпадать.

## 2. Как проходят реальные сделки по нишам

### Магазин, e-commerce, маркетплейсы, розница и B2B-опт

`Лид/витрина → Party → SalesOrder → OMS → резерв → WMS сборка/доставка → финансовое обязательство → оплата → возврат или закрытие → аналитика`.

- Импорт заказа: webhook/poll → **idempotent order inbox** с внешним ID, проверка сопоставления внешнего артикула с SKU, затем атомарный SalesOrder/OMS.
- Единый физический товар при FBS: разрешённая к размещению суммарная величина по независимым витринам **не выше** доступного запаса на связанном складе; нельзя рекламировать последнюю единицу сразу на трёх площадках.
- Перераспределение запасов идёт по подтверждениям API: **сначала уменьшение старого канала → подтверждение → увеличение нового**; при устаревшем feed или неопознанном товаре публикация должна снижаться до 0/блокироваться. Подтверждение API не равнозначно мгновенной видимости покупателю.
- FBO/FBW или собственность 3PL-клиента: физически и юридически отдельный запас. Не суммировать с доступным собственным FBS без подтверждённого перевода владения/локации.
- Две покупки одновременно → row lock/резерв по `tenant_id + warehouse_id + sku_id`; вторая получает backorder либо альтернативный склад, но не отрицательный остаток. Повторный webhook не создаёт второй заказ или второе списание.
- Закупка → PurchaseOrder → Goods Receipt / WMS приёмка → ledger; для опта нужны валюта, договор, кредитный лимит и дебиторка (принятие/срок/оплата контролируются Finance).
- 1 млн SKU: курсорная пагинация по индексированным ключам, отдельные серверные поисковые запросы и ограниченные выборки; **запрещён** рендер 1 млн строк, OFFSET на большой глубине, и импорт 1 млн строк в одной DB-транзакции.

### Салон красоты, барбершоп, маникюрная студия, фитнес, танцевальная школа

`Новый клиент → направление/услуга → мастер/тренер+ресурс+временной слот → запись → абонемент/предоплата → факт посещения и расходников → закрытие → начисление сотруднику → маржа и документы`.

- Ресурсная доступность: единая блокировка для одного мастера/зала/поста; вместимость занятия ограничена и на API, и в БД.
- Бронь/отмена/перенос: проверка правил тарифов, срока действия абонемента и дедлайна; отмена после начала урока не равняется бесплатному возврату.
- Абонемент: `AVAILABLE → RESERVED → CONSUMED | RELEASED`. Повторная отметка, конкурирующие записи и retry не должны дважды потреблять визит. Заморозка и отработка — отдельные правила со сроком и причиной.
- Урок завершён только после фиксации посещаемости; операционный snapshot → заработанная выручка, фактические материалы/аренда/тренер, обязательства; накопленные зарплатные ведомости утверждаются отдельно.
- Выход из группы или пауза → отмена будущих записей и их резервов в **одной транзакции**, иначе возможны «призрачные» занятия и долги.
- Персональные расчёты сотрудника доступны ему самому; остальные зарплаты, долги клиентов и согласованные скидки не выводятся без отдельного финансового разрешения.

### Автосервис и разборка запчастей

`Обращение/автомобиль → диагностика → заказ-наряд и согласование сметы → пост/механик/запчасти → фактические работы → акт → гарантия → расчёт`.

- Не передавать детали на ремонт из чужого склада/3PL: owner and tenant alignment обязательно.
- Разборка: донор-автомобиль → уникальная пригодная запчасть с состоянием/местом/серийным идентификатором → резерв → продажа. Одна деталь не может продаваться дважды.
- Согласование добавочных работ отделено от списания склада и оплаты: без подтверждения клиента не повышать сумму заказ-наряда автоматически.
- История VIN и клиентских данных видна только компании и уполномоченным сотрудникам.

### Веб-студия, SEO/PPC/SMM, маркетинговое агентство, профессиональные услуги

`Лид → коммерческое предложение → подписанный договор → проект/этапы → задачи и трудозатраты → результат → клиентское принятие → акт/счёт → оплата и P&L`.

- Доход retainer учитывается по условиям договора и периоду оказания; рекламный бюджет клиента не превращается в выручку агентства.
- Подтверждение клиентом результата должно иметь источник, время, идентификатор согласующего, версию и доказательство.
- Затраты на людей фиксируются снапшотом ставки за период; изменение ставки сегодня не должно переписывать уже закрытый месяц.
- Недосогласованные этапы, просроченные акты и отрицательная маржа попадают в очередь решений руководителя.

### 3PL/WMS-оператор

`Договор владельца груза → ASN/поставка → приёмка и контроль качества → размещение → задания отбора → упаковка → отгрузка → складская сверка → тарификация хранения/операций`.

- Каждая товарная позиция относится к tenant + owner + складу + локации; чужой собственник не может резервировать её через OMS.
- Незакрытые задания и разница инвентаризации блокируют автоматическое принятие остатков.
- Комиссии за хранение и операции рождают payable/receivable Finance, а не «списываются» из остатков.

## 3. Security: отказоустойчивая модель доверия

1. **Аутентификация:** сессия из случайного секрета; в БД только хеш, Argon2id для пароля, активная проверка членства организации и отзыв сессий при увольнении/компрометации. Вход ограничен по IP и учётной записи. Ограничить время жизни сессии и ротацию секретов.
2. **Tenant identity:** только middleware получает `tenant_id` из подтверждённой сессии. Игнорировать tenant ID из body/header/URL как способ расширить область запросов.
3. **Ролевая модель:** server-side permissions плюс `own/team/branch/all`, причём несколько ролей объединяются детерминированно. Отдельные `finance.read`, `finance.write`, `payroll`, `catalog.cost`. Наличие ссылки в UI не является проверкой прав.
4. **RLS:** все tenant-owned таблицы имеют RLS-политику; `SET LOCAL app.tenant_id` только внутри транзакции. Производственная роль не SUPERUSER, не BYPASSRLS, не владелец tenant-таблиц. Foreign key должен связывать сущности с **тем же tenant**, а не только с глобальным UUID.
5. **Привилегированные функции:** `SECURITY DEFINER` с фиксированным search_path, только явно разрешённые роли и сигнатуры; `PUBLIC EXECUTE` запрещено. Worker-сквозные функции, возвращающие зашифрованные секреты маркетплейсов, подлежат отдельной проверке роли и EXECUTE; не использовать тот же мощный DB-login для публичного API без оценки рисков.
6. **API/CSRF/transport:** cookie Secure+HttpOnly+SameSite в production, fail-closed Origin для мутирующих browser-запросов, строго ограниченный CORS, TLS/HSTS на reverse proxy, безопасные CSP и лимиты JSON-body/upload.
7. **Конфиденциальные поля:** зарплаты, себестоимость, данные клиентов, документы, ключи API и банковские реквизиты возвращаются только если разрешена конкретная операция; field-level маскирование на сервере.
8. **Задачи и файлы:** вирусная проверка и тип/размер, приватное object storage с подписанными временными URL, tenant-bound object keys, антивирус и лимиты ресурсов парсинга. Не хранить upload в публичной статики; логировать метаданные, не документы.
9. **Подключения:** секреты зашифрованы в БД, ключи расшифровывает только выделенный процесс-потребитель, исходящие адреса/providers разрешены по allowlist, контроль rate limits. Никаких ключей или provider ciphertext в журнале ошибок.
10. **Журнал:** неизменяемые события для смены прав, платежа, возврата, резерва, возврата абонемента и выгрузки персональных данных; журнал сам tenant-scoped; admin/security audit отделён от обычного событийного логирования.
11. **Защита инфраструктуры:** резервные копии зашифрованы и регулярно тестируется восстановление (RPO/RTO), отдельные роли мигратора/API/воркера, минимальные firewall ports, регулярное обновление зависимостей, секреты не в репозитории.

**Безопасность не подтверждена без** отрицательных запросов user A → tenant B для READ/WRITE/EXPORT/SEARCH/WebSocket/API/worker; проверки статуса membership; проверки всех SECURITY DEFINER grants; тестов на SSRF/XSS/injection; независимого pentest на staging.

## 4. Согласованность и масштабирование

- **Одна операция — одна бизнес-команда:** команды проверки, захват DB-lock, изменение источника истины, запись доменного события/outbox, commit. Ни внешний API, ни email не вызываются в длинной транзакции.
- **Outbox/workers:** асинхронная отправка событий по tenant, idempotency на `(tenant,provider,external_id)`, `FOR UPDATE SKIP LOCKED`, bounded retries с jitter и DLQ; пользователь видит статус и кнопку безопасного повтора.
- **Платёж:** уникальный provider/payment id + immutable ledger; повтор вебхука = тот же результат, изменение суммы = конфликт и ручная сверка.
- **Остаток:** отдельные `physical/reserved/safety/published`. Публикация на стороннюю площадку eventual consistent; гарантировать «нулевой риск двойной продажи» невозможно, но можно ограничивать экспозицию, резерв, очередь и безопасность при разрыве связи.
- **1 млн SKU:** базовые индексы `sku(tenant_id,id) WHERE ACTIVE`, GIN trigram для SKU/штрихкода/названия, `page limit <=200`, запрет COUNT на каждый запрос, cursor-based navigation, асинхронные import/export (чанки 1–5 тысяч, checksum/checkpoint, без пересоздания всех SKU), серверное autocomplete.
- **1 000 одновременно:** это 1 000 активных пользователей/сессий, **не** 1 000 подключений к PostgreSQL. Reverse proxy → несколько реплик Next/API → Redis shared limits → PgBouncer transaction pooling → PostgreSQL (определённый max_connections) → workers с отдельным budget.
- **Контроль перегрузки:** лимит дорогих запросов на tenant и пользователя, лимит тяжёлых отчётов, 429/503 + Retry-After, ограниченный DB queue, 3–5-секундный timeout коротких OLTP, отчёты и экспорты в job queue.
- **База:** partition/archive для больших append-only ledger и событий, индексы по `tenant_id + lookup key`, EXPLAIN ANALYZE BUFFERS, VACUUM/ANALYZE, мониторинг bloat/locks/deadlocks, PgBouncer. Реплика чтения — только если freshness и RLS позволяют.
- **Шардирование:** не нужен преждевременный tenant-per-database; предусмотреть migration path «крупный tenant на отдельный кластер» с теми же API-контрактами и кодом tenant-scoping.

## 5. Release-gates: что измерить вместо обещаний

| Испытание | Минимальный критерий для пилота | Статус |
|---|---|---|
| 2 организации × разные роли | 0 утечек и 0 несанкционированных модификаций, включая экспорт и поиск | Требуется запуск tenant-isolation SQL/API |
| 1 000 уникальных авторизованных сессий | 1 000 независимых токенов; ошибки ≤0,5%, p95 чтения ≤1,5 сек (целевой ориентир, не измеренный факт) | Есть `scripts/load-1000-sessions.mjs`; требуется запуск на staging |
| 1 млн SKU в одном tenant | 100–200 SKU/page, p95 < 250 мс на индексированную страницу при устойчивом staging-нагружении; поиск отдельно | Есть индексы и keyset; проверить реальными данными |
| Параллельные покупки одного товара | 0 отрицательных доступных остатков и 0 двойных списаний | Требуется интеграционная конкурирующая симуляция |
| 100 одинаковых webhook/payment callbacks | Ровно 1 заказ/платёж и воспроизводимый ответ | Требуется DB/provider sandbox |
| Прерванный worker и повторный запуск | Нет двойного списания; outbox возвращается в очередь, stale lease очищается | Требуется fault-injection |
| Restore backup | RPO/RTO измерены; restore выполнен в отдельный кластер | Не подтверждено |
| Тяжёлый tenant vs маленький tenant | Нет монополизации всего пула или worker; очереди и rate limits изолируют шумного клиента | Требуется multi-tenant soak test |

**Запрет на коммерческое обещание:** не объявлять поддержку 1 млн SKU и 1 000 конкурентных пользователей проверенной до воспроизводимых тестов, фиксирующих конфигурацию сервера, профили трафика, percentiles, DB-метрики, отказы и повторные попытки.

## 6. Поэтапный вывод в эксплуатацию

1. **P0 / защита данных:** production runtime DB-role audit, RLS и tenant isolation SQL gate, deny-by-default экспорт, field-level finance permissions, credential decrypt/worker segregation, baseline secrets/tokens/security headers.
2. **P0 / бизнес-корректность:** инварианты запасов и абонементов, финансовая идемпотентность, race tests, операции отмены/возврата, проверка 2+ конкурентных транзакций.
3. **P1 / скорость:** реальный миллионный каталог staging, индексы/explain, пагинация всех списков, 1 000 сессий, DB pool budget, workload isolation, import chunking.
4. **P1 / recovery:** DLQ/интерфейс повторов, мониторинг outbox и публикации запасов, PITR, restore rehearsal, автоматический security/economics go-live checklist.
5. **P2 / отраслевой UX:** «мой рабочий день» по роли и нише, прогрессивная настройка, один операционный центр исключений, информативные пустые состояния и безопасные массовые действия.

## 7. Проверенные элементы репозитория и непроверенные допущения

В коде найдены: `AuthorizationService.resolveScope`, global `PermissionGuard/AuthGuard`, `BrowserOriginGuard`, RLS tenant DB service, `ApiRateLimitGuard`, `RuntimePressureService`, миграция `222_catalog_million_sku_indexes.sql`, keyset `GET /catalog/products/page`, `scripts/security_tenant_rls_gate.sql`, `scripts/security_runtime_function_gate.sql`, `scripts/load-1000-sessions.mjs`.

Не подтверждено в этой сессии: выполнение реального PostgreSQL/Redis/worker на production, запуск всех Jest/TypeScript проверок, результаты независимого пен-теста, реальные API-интеграции провайдеров, восстановление бэкапов и фактическая способность нынешнего сервера обслужить описанные SLO.

**Согласование:** изменения бизнес-правил/БД проходят миграции с сохранением checksum, релизы — через staging / backup и ручной gate; без CI Actions согласно принятому проектному процессу.
