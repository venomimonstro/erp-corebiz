# CoreBiz — применение практик YCLIENTS и МойСклад
Дата: 13.10.2026. Статус: аудит исходников и дополнительные защитные тесты, не промышленный GO.

## Принцип переноса
Переносим принципы работы, не копируем интерфейс или закрытый код стороннего продукта. Общие объекты (party, service_resource, service_booking, catalog, inventory ledger, financial_obligation, service_package) должны оставаться едиными для всех ниш.

| Эталонная практика | CoreBiz | Усиление / критерий проверки |
|---|---|---|
| YCLIENTS: календарь по сотруднику и ресурсу, перерывы, лист ожидания | Service Booking/Resources, Dance Group | Поле мастер + зал блокируется одним подтверждением; проверка конкурирующих записей, часовых поясов, повторных запросов |
| YCLIENTS: услуга со своей ценой и длительностью для мастера | service_delivery_rule | Availability и createBooking используют одни правила; цена фиксируется на момент визита |
| YCLIENTS: абонементы и списание посещений | service_package, dance_package_redemption | Права посещения появляются только согласно политике активации. Резерв и фактический расход посещения — разные состояния |
| YCLIENTS: разграничение ролей менеджера и владельца | DANCE_MANAGER и DANCE_CUSTOMER | Менеджеру — записи и долги клиентов, не банковские счета и зарплата; клиенту — только собственная семья |
| МойСклад: заказ ≠ физическая отгрузка | Sales / OMS / Inventory | Заказ/резерв не должны уменьшать физический остаток. Отгрузка — отдельный ledger-event |
| МойСклад: доступно = остаток − резерв с учётом правил | reservation-policy и OMS | Нельзя обещать последний товар нескольким каналам; safety stock проверяет сервер |
| МойСклад: пополнение резерва через закупку | Purchases/Inventory | Рекомендации по закупкам используют реальные доступные остатки и ожидания, а не общую «цифру на складе» |
| Общий бухгалтерский контроль | Finance/Obligations/Accounting | Выполнено ≠ оплачено ≠ фискализировано; без provider reconciliation статус UNKNOWN, без выдуманной чистой прибыли |

## Особый кейс: московская студия танцев
Исходные допущения: 2 филиала, 12 направлений, 52 тренера, 3 зала в первом филиале, 700 000 ₽/месяц аренды филиала А, два менеджера по 50 000 ₽, оборот около 3 млн ₽, один групповой визит 2 400 ₽, пакет 10 занятий 7 000 ₽, индивидуальное 3 500 ₽. Расходы филиала Б, ФОТ тренеров, налоги, субарендные платежи и сезонные коэффициенты НЕ определены. Нельзя утверждать чистую прибыль или факт оплаты абонемента по этим вводным.

Путь: регистрация → тариф → профиль DANCE_FITNESS → филиалы/залы/права → 52 ресурса тренера и их реальные учётные записи → направления/услуги/цены → графики/группы/зал → клиент/плательщик/семья → абонемент → запись → явка → списание → обязательство → подтверждение оплаты → зарплата/аренда → отчёт по филиалам.

Особо проверять:
1. 50+ тренеров и 2/2 менеджеров без конфликтующих смен.
2. Раздельную занятность большого зала и оплачиваемую сдачу малых залов; входящая субаренда не равна расходу по договору владельца.
3. Менеджер может показать долги ученика, но не видит зарплаты и все банковские операции.
4. Плательщик видит только назначенных учеников, их занятия/остатки пакетов и сверенные начисления.
5. Увольнение тренера требует переназначить будущее расписание, не переписывает посещения и уже начисленные выплаты.
6. Завершение урока и пакетное списание идемпотентны, без повторных затрат.

## Что добавлено
`scripts/competitor-cross-vertical-contract.test.mjs` проверяет в исходниках связность главных инвариантов YCLIENTS+МойСклад: ограничения ATP, резерв и отгрузка, ограничения расписания и идемпотентности, состояние абонементов и посещений, честный финансовый статус клиентского кабинета, права менеджера, nullable-бюджет.

`scripts/release-check.sh` теперь включает этот офлайн-тест. Важно: **тест наличия и связности защитных конструкций не доказывает их работу в запущенной БД или полноценность продукта**.

## Продакшен-барьеры
Нужны `pnpm typecheck && pnpm test && pnpm build`, отдельная disposable API/PostgreSQL/Redis, HTTP E2E владельца и менеджеров, реальные негативные транзакционные тесты и провайдеры платежей/кассы/доставки только в sandbox. Никакие искусственные регистрации и движения товара не запускать против реальных клиентов.
