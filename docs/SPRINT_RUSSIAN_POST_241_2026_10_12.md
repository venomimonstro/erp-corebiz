# CoreBiz sprint 241 — Почта России: договор, API и тарифы

Дата 12.10.2026. Реализация исходников в `main`, без CI/GitHub Actions.

## Что доступно

- `/app/settings/integrations/post`: выбрать сайт продавца, сохранить
  доступ к официальному API «Отправка», проверить авторизацию и
  получить расчёт тарифа.
- Интеграция использует реальные заголовки:
  `Authorization: AccessToken <API_TOKEN>`;
  `X-User-Authorization: Basic <GENERATED_USER_AUTH_KEY>`.
- HTTP endpoint зафиксирован:
  `POST https://otpravka-api.pochta.ru/1.0/tariff`.
  Переадресации запрещены, 10 секунд таймаут, ответ ограничен
  по размеру. Динамические URL клиент не передаёт.
- Сейчас предлагается только `POSTAL_PARCEL`,
  `mail-category=ORDINARY`, `payment-method=CASHLESS`.
- Почтовые индексы — строки из шести цифр с сохранением ведущих
  нулей в CoreBiz; вес 1–20 000 грамм.
- Тариф — исключительно суммы провайдера `total-rate` и
  `total-vat` в **копейках**, без искусственного расчёта.
  Если API не подтвердил цену/НДС, тариф не показывается.
- Для каждого интернет-магазина отдельные токен и ключ:
  AES-GCM ciphertext, tenant-RLS, scope `sites.manage=all`.
  Повторное сохранение выключает подтверждённый статус.
- Только успешный тарифный запрос переводит соединение в
  `VERIFIED`; новый quote имеет срок 15 минут и
  хранится в `commerce_post_tariff_quote`.
- Миграция `241_russian_post_tariff_quotes.sql`.

## Что НЕ готово (не показывать пользователю «доставка подключена»)

- Подтверждённая приёмка отправления Почтой России;
- Создание заказа `orders`, партия, сортировка, ярлык, ШПИ;
- Трекинг, автоматические статусы и возвраты;
- Наложенный платёж, страховка, особые категории;
- Checkout-получатель, адресная нормализация, ПВЗ/ОПС;
- Сверка поступления денег/чеков и реальных расходов на отправку.

Для этих функций требуется отдельная безопасная
`shipping_order`-модель с защитой от повторной отправки и
реальные тестовые операции на договоре клиента. **Расчёт
стоимости не создаёт посылку.**

## Стабилизация АТОЛ — предыдущий этап

В актуальном `main` уже существует миграция
`240_atol_fiscal_reconciliation_queue.sql` и
`AtolReceiptsService.pollReports()`. Это GET-only очередь сверки
ранее отправленных чеков, не очередь повторного создания кассовых
документов. Оставлена **одна** миграция №240; конфликтующая
`240_atol_report_poll_queue.sql` удалена.

Для фоновой проверки вручную включается:

```dotenv
COREBIZ_ATOL_REPORT_POLL_ENABLED=true
COREBIZ_ATOL_REPORT_POLL_INTERVAL_MS=60000
```

Только после применения миграций, проверки безопасности и
рабочего тестового окружения. Для реальных касс фискальные
feature flags остаются заблокированными до испытаний.

## Порядок установки на staging

1. Резервное копирование и тестовое восстановление БД.
2. Применить миграции строго 234–241 по одному разу.
3. Проверить, что миграция `240` в каталоге существует только
   с именем `240_atol_fiscal_reconciliation_queue.sql`.
4. `pnpm typecheck && pnpm test && pnpm build && pnpm stability:check`.
5. Подключить собственный API-токен и Basic-ключ Почты России.
   Сделать 1 тарифный запрос и сравнить цену с личным кабинетом
   «Отправка» для того же договора, маршрута и веса.
6. Тесты: 2 tenant-а, разные договоры, чужой сайт, запрос
   без `sites.manage=all`, истёкший токен, 401/429/500,
   таймаут, неверные денежные поля, ведущий ноль в индексе.

В этой сессии реальные провайдерские аккаунты и PostgreSQL
не доступны; поэтому источник не аттестован как
production ready и не выполнялись E2E транзакции.
