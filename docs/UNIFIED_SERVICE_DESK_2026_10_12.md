# Sprint: Unified Service Desk (2026-10-12)

## Результат

Реализовано единое рабочее место для сервисных компаний
`/app/service/desk`. Это **UI-объединение существующих модулей**;
новый финансовый ledger, «вторая CRM», новый календарный движок
и копия расчёта зарплат НЕ создавались.

Разделы в одной странице:
- **Журнал**: 7-дневный обзор, фильтр сотрудников, статус визита,
  карточка с материалами, обязательствами, счётом, возвратами.
- **Настройка**: создание услуги/цены/длительности,
  нового специалиста, безопасный шаблон недельного расписания,
  клиента CRM, индивидуальной цены мастера через
  существующий `service_delivery_rule`.
- **Клиенты**: доступная по RBAC единая CRM, история визитов и
  накопленная стоимость завершённых посещений (не «факт оплат»).
- **Экономика**: выручка по завершённым услугам, расходники,
  начисления сотрудникам, вклад услуг и возвратность. Финансовые
  данные не выдаются без `finance.read`.

Навигация: CoreBiz Sidebar → «Рабочее место услуг», а
`/app/start` для `BEAUTY_SALON`, `NAIL_SALON`,
`BARBERSHOP` ведёт прямо сюда. Прежние страницы
`/app/service`, `/app/service/bookings`,
`/app/service/setup`, `/app/service/team` работают отдельно
и остаются для продвинутых операций.

## Безопасность и транзакционная целостность

1. Запись всегда создаёт `POST /service/bookings`; доступность
   до отправки проверяется `GET /service/availability`.
   Сервер остаётся арбитром квалификации, ресурсов и занятости.
2. Если результат POST неизвестен из-за сетевого сбоя, ключ
   идемпотентности сохраняется в памяти формы; повтор допустим
   только для идентичных параметров записи. Пользователю
   показано сообщение о необходимости сверить журнал.
3. Статусы `CANCELLED`, `COMPLETED`, `NO_SHOW`
   требуют отдельного подтверждения. Запрос передаёт текущую
   версию; сервер отклоняет неверную последовательность.
4. `BookingService.bookings` и `BookingService.bookingDetails`
   теперь скрывают `billing`, `refund`, `settled_minor`,
   `invoice_status`, `price_minor_snapshot` и связанные
   финансовые поля без `finance.read`; логистика остаётся
   доступной `service.read`. Добавлен
   `booking-finance-privacy.spec.ts`.
5. Персональные цены мастеров записываются в существующие
   правила предоставления услуги; цена и длительность
   snapshot-ятся сервером при бронировании. Уже оформленные
   визиты нельзя пересчитать простым редактированием каталога.

## E2E

- `scripts/service-desk-browser-journey.mjs`: регистрация
  владельца салона → создание услуги → мастер → график →
  индивидуальная цена → клиент → реальный доступный слот →
  запись → подтверждение итоговой цены по API → история
  клиента → экономика → мобильный экран 390px.
- `scripts/owner-business-setup-e2e.mjs`: проверяет цену
  мастера в `service_booking.price_minor_snapshot` и в
  `service_booking_charge`, последовательно выполняет
  ARRIVED→IN_SERVICE→COMPLETED и проверяет сервисную
  profitability-проводку и отсутствие ложной отметки оплаты.
- Скрипт владельца исправлен на штатный NestJS HTTP 201
  для успешных POST, 200 для GET/PATCH/PUT.
- `scripts/production-gate.sh` теперь запускает оба теста
  вместе с прежним пользовательским E2E. В
  `scripts/release-check.sh` проверяется синтаксис новой
  браузерной симуляции.
- `scripts/stability-source-preflight.mjs` предотвращает
  случайное удаление ключевых UI/API-инвариантов.

**Блокер:** тесты выше требуют disposable API/PostgreSQL,
миграции, Playwright/Chromium и запуск браузера.
В GitHub выполнялись коммиты и отдельная статическая
синтаксическая проверка скриптов. **Работающий E2E PASS и
проверенный `pnpm typecheck/test/build` не заявляются.**

## Запуск на строго disposable окружении

```bash
git checkout main && git pull --ff-only origin main
corepack enable
pnpm install --frozen-lockfile
pnpm typecheck && pnpm test && pnpm build
```

API/WEB должны работать на тестовых портах 4000/3000
**против одноразовой БД и тестового Redis**:

```bash
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_BASE_URL=http://127.0.0.1:4000 \
COREBIZ_SMOKE_WEB_ORIGIN=http://localhost:3000 \
node scripts/owner-business-setup-e2e.mjs

COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_WEB_URL=http://localhost:3000 \
node scripts/service-desk-browser-journey.mjs
```

Это мутационные сценарии, **на production нельзя**.

## Что ещё нужно до полноценного уровня YCLIENTS

1. Стабильный appointment panel c несколькими услугами,
   перетаскиванием и серверной optimistic locking.
2. Публичная универсальная форма выбора любой услуги,
   мастера и слота с TTL-hold и подтверждением.
3. Обязательное подключение настоящих эквайринга,
   фискализации и автоматического закрытия неопределённых
   `UNKNOWN` с provider reconciliation.
4. Миграция из YCLIENTS с dry-run/dedupe/preview,
   календарь смен/отпусков, уведомления -24ч/-2ч,
   виджет лояльности и личный кабинет клиента.
5. Проверка B2B multi-tenant RLS, одновременной записи,
   нагрузочного P95/P99, mobile/keyboard accessibility
   и 30-дневного доступности SLO.

**Статус:** объединённый интерфейс и целевые регрессионные
тесты добавлены в `main`; коммерческий запуск ещё требует
реальных стендовых испытаний.

## Дополнение: масштабирование расписания и часовые пояса

- Новый query-параметр `GET /service/availability?resourceId=UUID`
  ограничивает выборку SQL конкретным сотрудником **до** лимита
  500 слотов. Без параметра API сохраняет прежнее поведение.
  UUID валидируется, tenant и RBAC-фильтры сохраняются.
- Рабочее место запрашивает availability одного специалиста,
  а не всех сотрудников. Для выбора локального дня используется
  IANA-часовой пояс ресурса; при запросе UTC-интервал расширен,
  результат фильтруется по локальной дате мастера.
- Список записей выбирается с небольшим запасом вокруг недели
  и затем группируется по часовому поясу ресурса, чтобы визиты
  на границах суток не пропадали у владельца из другой страны.
- Добавлен `booking-availability-resource.spec.ts`:
  фильтрация до лимита, обратная совместимость запроса без
  resourceId, отклонение неверного UUID без обращения к БД.
- Browser-симуляция принудительно использует
  `America/New_York` при часовом поясе тестового салона
  `Europe/Moscow` и проверяет создание визита через реальные
  доступные интервалы.

**Ограничение:** это корректность отображения даты и выбора слота
для индивидуальной записи; высоконагруженный генератор доступности
(много сотрудников × месячный горизонт) требует отдельной
оптимизации bulk SQL и замеров на стенде. Не следует объявлять
реальный P95/P99 без нагрузочного прогона.
