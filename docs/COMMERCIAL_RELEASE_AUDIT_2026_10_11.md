# CoreBiz — комплексный коммерческий release-аудит
Дата: 2026-10-11 · Branch: `main` · CI/GitHub Actions намеренно не используются.

## Вердикт

**NO-GO для массового платного SaaS и интернет-магазинов с онлайн-оплатой.**
Допустим только ограниченный пилот на отдельной подготовленной среде после
прохождения обязательных проверок и уведомления участников об ограничениях.
Код и наличие тестов — не доказательство runtime PASS. Аудит выполнен на
исходниках репозитория; запустить `pnpm install/typecheck/test/build` и
восстановление реальной PostgreSQL в среде аудита не удалось, поэтому
утверждений о пройденных испытаниях нет.

## Реализованные исправления в ходе данного аудита

1. **Публичный заказ защищён от потока запросов**: тарифы
   `PUBLIC_CHECKOUT` (10 запросов/IP/мин) и `PUBLIC_CART`
   (45 запросов/IP/мин); отделены от доверенных интеграционных `WEBHOOK`.
   Те же консервативные лимиты применены к публичным CRM/booking-формам.
2. **Складское наличие** публичной витрины учитывает только активные склады
   и `inventory_policy.enabled=true`; readiness сопоставляет валюту магазина
   и SKU. Закрытый источник теперь не выглядит как товар в продаже.
3. **Самостоятельная активация платных SaaS-тарифов без оплаты закрыта**.
   `billing/select-plan` не даёт перейти на новый платный план без
   провайдерного подтверждения. Переход на бесплатный и идемпотентный
   запрос текущего плана остаются допустимыми. UI не обещает
   несуществующее автоматическое списание.
4. **Интернет-магазин не открыт, пока не опубликована главная**:
   новая миграция `226_public_storefront_publication_gate.sql` сохраняет
   SECURITY DEFINER разрешения и отказывает анонимному разрешению
   витрины/созданию новых корзин до публикации.
   Checkout дополнительно проверяет опубликованную страницу.
5. **Корзина не блокируется архивными товарами**: такие строки видны
   и их можно удалить, но оформить их как активные нельзя.
6. **Контактные поля** валидируются сервером до создания Party/Order.
   Каталог при оформлении перепроверяется; несовместимые позиции
   вызывают Conflict, а не создают неподтверждённый заказ.
7. **Идемпотентность импорта** привязана к содержимому файла и типу данных.
   Повторный ключ с другими байтами/типом получает Conflict, а не
   успешный ответ от старого файла. Тяжёлому импорту назначен
   `EXPENSIVE`-бюджет.
8. **Релизный тестовый скрипт не может случайно тестировать публичные
   URL**: `scripts/production-gate.sh` требует loopback-адреса
   для API/browser smoke, поскольку тестовые сценарии могут
   создавать бизнес-данные.
9. Добавлены регрессионные тесты для rate guard, checkout, импорта,
   ограничения платных тарифов, складского ATP.
10. Без GitHub Actions, без отключения RLS, без прямого изменения
    денег/бухгалтерии/действующих заказов на боевом сервере.

## Критические незакрытые задачи

### P0 — нельзя продавать как полноценный платный сервис

- **Платёжная система SaaS**: защищённый checkout, webhook с проверкой
  подписи/статуса/суммы/валюты, реестр событий, идемпотентность,
  изменение subscription entitlement только после подтверждения
  провайдером, возвраты/отмена/повторные списания по правилам.
- **Полноценная онлайн-оплата интернет-магазина**: отдельный payment state,
  частичные оплаты/возвраты, предотвращение двойного списания; не путать
  подтверждённый SalesOrder и `payment_status=PAID`.
- **Доставка и самовывоз**: выбор способа, тарифов, адреса/ПВЗ, статусы,
  трек-номера, возврат доставки, интеграции с перевозчиком.
- **Чеки, налоги и учёт**: проверить применимые 54-ФЗ/ККТ/ОФД,
  бухгалтерскую точность, банк, налоги/НДС и регламентированные
  формы с экспертом и эталонными данными.
- **Восстановление доступа и уведомления**: завершённый пользовательский
  тест восстановления пароля, email подтверждений, изменения телефона,
  отправки заказных событий и bounce handling.
- **Tenant isolation**: unprivileged SQL role (NOSUPERUSER, NOBYPASSRLS),
  cross-tenant read/write/export/search, cookies, Origin/CSRF, домены.
- **Собственные домены**: проверка A/CNAME/связывания/HTTPS,
  сертификатов и автоматического обновления, корректность Host routing;
  подтверждение TXT само по себе не гарантирует рабочий HTTPS.
- **Release evidence**: полный прогон disposable migrations,
  typecheck, tests, build, business journeys, concurrency, backup/restore,
  минимальный нагрузочный baseline.

### P1 — повышает конверсию и удержание

- Drag-and-drop уровня коммерческого конструктора, мобильная адаптация,
  темы и галереи/загрузка файлов в собственный storage.
- Варианты товаров/характеристики/фильтры, категории с ЧПУ, SEO product
  schema, правила 301 redirects.
- Скидки/промокоды, повторный заказ, восстановление корзины.
- Показ маржи после возвратов и переменных расходов, товар в пути,
  контроль закупок и предупреждение дефицита.
- Упрощённый нативный onboarding для малого бизнеса за один день.

## Важное решение по продукту

Интеграция с 1С / CommerceML, копирование громоздкой 1С-логики,
автоматическая загрузка бухгалтерских архивов **не требуются**.
Достаточно простого CSV/XLSX импорта товаров, затем — удобные
инструменты продаж, склада, закупок, своего магазина и управления прибылью.

## Приёмка перед пилотом и коммерческим запуском

1. На отдельной БД выполнить все миграции с нуля и upgrade replay
   исторической структуры; перед боевым обновлением backup.
2. `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`,
   `pnpm build`, `pnpm stability:check`.
3. Два tenant, два браузера, одна runtime БД роль:
   запреты cross-tenant, прямых SQL-функций и privilege escalation.
4. Создание магазина → публикация → DNS TXT → A/CNAME → HTTPS,
   проверка canonical/robots/sitemap/страницы на домене.
5. Корзина старого/архивного товара, два конкурентных checkout,
   retry после network timeout, отмена/reservation/reconciliation.
6. Платный план нельзя получить без подтверждённого платежа,
   пользователю доступно только честное объяснение.
7. Пробная операция с PSP (только sandbox), дубликаты/подписи вебхука,
   возврат, финконтроль; фискальный сценарий в sandbox.
8. Доставка: ПВЗ/адрес/стоимость/срок, невозможность сменить сумму
   после подтверждения без нового согласия покупателя.
9. Бизнес-сценарии торговли, услуг, склада и 3PL на desktop/mobile.
10. Backup → restore в чистую БД, сверка ledger/WMS/финансов,
    smoke на loopback, продемонстрированный rollback.
11. Pilot 5–10 компаний с реальными операциями и hypercare
    перед публичной продажей.

## Команды (без CI)

Статические и модульные проверки запускаются локально, **не меняют боевые
бизнес-данные**:

```bash
git checkout main && git pull --ff-only origin main
corepack enable
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
pnpm stability:check
node scripts/migration-preflight.mjs
```

Полный runtime-gate запускается **только на disposable/staging** с
подтверждёнными тестовыми DATABASE URLs и локальными (loopback)
`COREBIZ_SMOKE_BASE_URL` / `COREBIZ_SMOKE_WEB_URL`:

```bash
bash scripts/production-gate.sh
```

Не запускать этот gate на боевой базе: тестовые сценарии создают документы.
Не выводить результат `PASS` из того, что файл скрипта существует.
До настоящих интеграций оплаты, доставки, фискализации и runtime evidence
публичный коммерческий релиз остаётся **NO-GO**.
