# Сквозной контроль бизнес-процессов CoreBiz

Дата: 2026-10-11. Статус: реализован контроль исключений по исходным бизнес-данным, а не обещание, что все 16 ниш полностью готовы к коммерческому запуску.

## Единые правила для всех ниш

- Одна организация и один tenant_id на все CRM/продажи/запасы/оплаты/задачи. Сигналы по данным другого tenant запрещены.
- Владелец получает только незакрытые исключения в /app/operations. Предметные сотрудники — свои разрешённые события в общей очереди.
- Сигнал возникает из фактического состояния сущности; после исправления закрывается автоматически.
- Сканирование имеет ограничение 200 записей на тип и строку-сигнал переполнения. При неполном просмотре запрещено очищать уже зарегистрированные события.
- После активности владельца проверка обновляется не чаще раза в 15 минут; это не непрерывный мониторинг автономного воркера.
- Финансы и данные клиентов доступны только при соответствующих разрешениях. Оповещения не должны нарушать эту изоляцию.

## Вертикали и закрываемые исключения

| Ниша | Обязательный процесс | Контроль в текущем релизе |
| --- | --- | --- |
| Универсальный бизнес | CRM → заказ → деньги | CRM_ACTION_OVERDUE, SALES_UNFULFILLED, FINANCE_OVERDUE |
| Салон красоты | клиент → запись → мастер → расчёт | SERVICE_UNCLOSED, FINANCE_OVERDUE |
| Барбершоп | барбер → кресло → оказанная услуга | SERVICE_UNCLOSED, FINANCE_OVERDUE |
| Маникюрный салон | услуга → мастер → расходники → оплата | SERVICE_UNCLOSED, PROCUREMENT_OVERDUE |
| Автосервис | заказ-наряд → согласование → работы → выдача | AUTOMOTIVE_OVERDUE + лимит согласованных работ на уровне БД |
| Авторазбор | донор → SKU → склад → заказ | SALES_UNFULFILLED, PROCUREMENT_OVERDUE, WMS_TASK_FAILED |
| Студия танцев | группа → урок → посещение → абонемент → зарплата | DANCE_UNCLOSED, DANCE_MISSING_MARGIN + атомарные резервы |
| Профессиональные услуги | проект → задачи → результат → выставление | PROJECT_DELIVERABLE_OVERDUE, FINANCE_OVERDUE |
| Веб-студия и маркетинг (смешанный профиль) | CRM → договор → производство → приёмка | PROJECT_DELIVERABLE_OVERDUE, CRM_ACTION_OVERDUE |
| Веб-студия | разработка → сдача → приёмка → счёт | PROJECT_DELIVERABLE_OVERDUE, FINANCE_OVERDUE |
| Маркетинговое агентство | договор → ретейнер → отчёт → биллинг | PROJECT_DELIVERABLE_OVERDUE, FINANCE_OVERDUE |
| Розничный магазин | закупка → склад → продажа → отгрузка | PROCUREMENT_OVERDUE, SALES_UNFULFILLED |
| Оптовые продажи B2B | заказ → кредитный контроль → отгрузка → оплата | SALES_UNFULFILLED, FINANCE_OVERDUE |
| Интернет-магазин | свой сайт → OMS → склад → отгрузка | SALES_UNFULFILLED, MARKETPLACE_STOCK_BLOCKED |
| Продавец на маркетплейсах | сопоставление SKU → импорт заказа → ATP → остатки | MARKETPLACE_UNMAPPED, MARKETPLACE_STOCK_BLOCKED |
| Склад 3PL | приёмка → адресное хранение → задания → отгрузка → биллинг | WMS_TASK_FAILED, FINANCE_OVERDUE |

Общие нарушения поддержки: SUPPORT_ESCALATED. Для бухгалтерии дополнительно действуют BANK_UNMATCHED, VAT_UNREGISTERED, CLOSE_BLOCKED, PAYROLL_DRAFT.

## Сценарии для приёмки перед коммерческим запуском

1. Положительный: заказ переходит в исполнение; после отгрузки исчезает из просрочки.
2. Отрицательный: просроченная закупка остаётся на контроле, пока поставка не принята.
3. Положительный: урок закрыт, посещения списаны, снимок экономики существует.
4. Отрицательный: параллельные записи не превышают вместимость и не создают второй расход абонемента.
5. Положительный: SKU сопоставлен, остаток распределён без дублирования по площадкам.
6. Отрицательный: API маркетплейса не отвечает, система оставляет отказ и не изображает синхронизацию успешной.
7. Положительный: deliverable утверждён, из просроченных результатов исчезает.
8. Отрицательный: автомобиль нельзя согласовать по позициям выше явно заданного клиентом бюджета.
9. Положительный: изменить бюджет можно только с основанием; старый и новый лимит попадают в audit_event.
10. Отрицательный: сотрудник без finance.read не получает чужую выручку, договорные ставки или задолженность.
11. Положительный: сотни событий регистрируются пакетным SQL, без сотен последовательных запросов.
12. Отрицательный: при достижении лимита проверенных записей непросканированные проблемы не помечаются решёнными.

## Границы готовности

Проверки выше не заменяют end-to-end тесты с реальным PostgreSQL, API маркетплейсов, кассой, бухгалтерскими выгрузками, тестированием одновременных пользователей и восстановлением после отказа. Нельзя считать все вертикали production-ready только на основании этих изменений.

Порядок релиза: бэкап → зависимости → typecheck → Jest → миграции → сборка → тестовая проверка ролей, платежей и внешних API → перезапуск сервисов по конкретной конфигурации инсталляции.

Техническая реализация: `vertical-operational-rules.ts`, `dashboard.service.ts`, `action-queue.service.ts`, миграции 219–220. Новые изменения без CI/Actions, прямо в main.
