# CoreBiz — аудит владельца бизнеса и критерии SLO 99,9% (12.10.2026)

Статус: код исправлен в `main`; **не подтверждённые runtime-тесты, релиз NO-GO**.
Нет CI/Actions. Ни одной живой банковской/почтовой операции этот аудит
не выполняет. Исходники без собственного production-доступа не доказывают
доступность сервиса.

## Основные находки и исправления

| Критичность | Область | Проблема | Изменение |
|---|---|---|---|
| P0 | Интернет-магазин | Заказ можно было создать без способа получения, но последующая YooKassa-оплата требовала `commerce_order_delivery` | Checkout теперь отклоняет заказ до настройки самовывоза/доставки; отсутствие способа не создаёт Party/SalesOrder и снимает lease |
| P0 | Release simulations | 40 параллельных покупателей и golden ecommerce не создавали реальные merchant-способы получения и не проверяли их выбор | Сценарии настраивают самовывоз, запрашивают справочник и указывают действительный `deliveryMethodId` |
| P0 | Первый день владельца | Не было отдельного исполняемого маршрута «создание бизнеса → товар → склад → магазин → заказ → безопасный отказ платежа → отчёты → другой tenant» | `scripts/owner-first-day-journey.mjs`; включён в disposable production-gate |
| P1 | Auth/UI simulation | Старый smoke переходил на страницу входа с активной cookie-сессией | Перед тестом повторной авторизации cookies очищаются |
| P1 | Доказательство uptime | Нельзя было проверить заявленные 99,9% за скользящие 30 дней | `scripts/slo-availability.mjs` и unit tests; пропущенный минутный замер считается недоступностью |

## Программа проверки владельца

1. Регистрация, компания, личный кабинет, выбор профиля/вертикали.
2. Товар, цена, склад, остаток, повторное проведение корректировки.
3. Сайт, каталог, публичная корзина; отказ checkout без доставки.
4. Добавление самовывоза в настройках, сверка публичных вариантов,
   оформление заказа и повтор POST без второго SalesOrder.
5. Запрет оплаты без договора продавца с YooKassa, отсутствие ложного `PAID`.
6. Главная сводка и операционные показатели после заказов.
7. Создание второй компании и контроль отсутствия чужих заказов.
8. Golden-профили: торговля, e-commerce, сервис, танцы, автосервис,
   3PL, веб-студия, маркетинговое агентство, маркетплейсы.
9. Конкуренция 100 пользователей: 40 корзин/25 единиц товара,
   30 попыток занять один слот, 20 лидов и 10 межарендаторских чтений.

Эти сценарии **подготовлены в коде, а не пройдены в работающей среде**.
Тесты с внешними провайдерами, DNS/HTTPS, реальными пользователями,
импортом из 1С и чековыми сценариями — отдельная обязательная приёмка.

## Цель 99,9%: формальная модель

- 30 дней по 24 часа: `43200` минут.
- Бюджет недоступности: **не более 43 полных минут** за 30 дней.
- В мониторинге: 1 проверка в минуту, HTTP GET
  `/api/v1/health/ready`, HTTP 200 + `ok=true` +
  `data.status='ok'`, лимит 8 секунд.
- Пропуск замера/таймаут/ошибка/несогласованный HTTP не считается успехом.
- Сам по себе health endpoint проверяет только *один компонент*
  доступности: дополнительно нужны синтетические клиентские чтения,
  метрики успешных чек-аутов и ошибки PSP/ККТ/OMS по отдельным SLI.
- Показатель становится доказательством доступности только после
  **полных 30 дней** внешних измерений + анализа инцидентов.

Для эксплуатации требуются отдельные хосты приложения/мониторинга,
репликация/HA на уровне API и БД, бэкапы с проверенной реставрацией,
алерты на дубли платежей и несверенные `UNKNOWN` отправления,
ресурсные лимиты, runbooks с RTO/RPO и проверенный rollback.
Одиночный VPS без отказоустойчивых зависимостей **не может гарантировать**
99,9% при потере физического сервера/диска/сетевого провайдера.

## Локальная приёмка без GitHub Actions

На **отдельной disposable среде**, после создания резервной копии:

```bash
git checkout main && git pull --ff-only origin main
corepack enable && pnpm install --frozen-lockfile
pnpm typecheck && pnpm test && pnpm build && pnpm stability:check
pnpm slo:test
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_BASE_URL=http://127.0.0.1:4000 \
node scripts/owner-first-day-journey.mjs
```

Полный `bash scripts/production-gate.sh` запускать **только** с
заполненными URL двух **разных disposable PostgreSQL** и локального API/Web.
Он выполняет мутации, тесты, backup/restore и не является командой
production-обновления. Для успешного результата требуется его
machine-readable evidence-manifest, все обязательные проверки и
отдельное решение владельца о пилотном запуске.

### Внешняя минутная проверка SLO

Отдельный узел мониторинга с локальным долговечным storage,
строго по расписанию раз в минуту:

```bash
COREBIZ_SLO_BASE_URL=https://YOUR_ERP_HOST \
COREBIZ_SLO_EVIDENCE_FILE=/secure/path/availability.jsonl \
node scripts/slo-availability.mjs probe

COREBIZ_SLO_EVIDENCE_FILE=/secure/path/availability.jsonl \
node scripts/slo-availability.mjs report
```

Не размещать monitoring JSONL в публичном webroot. Должна быть
ротация/бэкап и защищённые права. `report` выходит с ненулевым кодом
при недостижении 99,9%.

## P0/P1 до реального commercial GO

1. Перепроверить миграции до 243 под реальной runtime ролью PostgreSQL,
   tenant RLS и сопоставить с журналом приложенных миграций.
2. Провести точные sandbox E2E: YooKassa/АТОЛ/СДЭК/Почта России,
   потерянные webhooks, таймаут после provider accept, возвраты.
3. Поставить автоматические алерты по платежным reconciliation
   `EXHAUSTED`, почтовым `UNKNOWN`, отвалу Redis и зависшим OMS-резервам.
4. Запустить pilot 5–10 компаний с контролируемой нагрузкой,
   ежедневной сверкой финансов/остатков, планом отката и восстановлением.
5. Собрать 30-дневную измеренную статистику аптайма и отдельные
   success-rate SLI для заказа/оплаты/доставки; только тогда делать
   утверждение о стабильности **99,9%**.

**Нельзя приравнивать** прохождение исходных unit tests или наличие
функций к фактически подтверждённому SLA.
