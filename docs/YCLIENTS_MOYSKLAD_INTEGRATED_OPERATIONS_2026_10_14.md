# CoreBiz · Сверка практик YCLIENTS и МойСклад: продолжение 14.10.2026

## Цель

Одна система для клиента, а не отдельные продукты «запись», «абонементы»,
«склад», «касса» и «аналитика». Для студии танцев это означает:
**направление → расписание → тренер/зал → ученик/семья → абонемент →
урок → посещение → обязательство/оплата → начисление тренеру →
расход зала → управленческий результат**.

Для магазина: **заказ → резерв → оплата → отгрузка →
движение остатка → возврат → финансовая сверка**.

## Принципы, которые нельзя нарушать

| Эталонный метод | Как должно работать в CoreBiz | Проверяемый инвариант |
|---|---|---|
| YCLIENTS: услуга + назначенные специалисты + персональные цена/длительность | Один service catalog и service_delivery_rule | Историческая цена фиксируется в визите; недоступный специалист не предлагает слот |
| YCLIENTS: карточка группового события | Урок, состав группы, присутствие, абонемент, товары, расчёты открываются из одного операционного контекста | Одинаковая операция не проводится дважды |
| YCLIENTS: техкарта к услуге и мастеру | Связь специалиста, материалов, норм и складского источника | Материал списывается по фактическому выполнению, не по предварительной записи |
| МойСклад: заказ не списывает остаток, отгрузка списывает | Раздельные заказ, резерв и фактическая выдача | Резерв не выдаётся за физическое списание |
| МойСклад: доступное/ожидаемое/фактическое | Inventory ledger + ATP + incoming | Нет отрицательного доступного остатка при конкуренции |
| Обе системы: документы/действия связаны | Единые связи по tenant, party, сотруднику, заказу/визиту, платёжному обязательству | Каждый отчёт проваливается к первичному документу |
| Семейный бизнес | Один плательщик, несколько учеников и получателей услуг | Родитель видит только доказанные родственные/платёжные связи |
| Несколько филиалов | Филиал, касса, склад, зал, услуги и цены — собственные атрибуты при общей CRM внутри tenant | Чужой филиал не раскрывается роли с branch scope |

## Доработка этого продолжения

1. **Запрос родительского кабинета:** при большом архиве посещений сервер
   раньше мог заполнить лимит в 250 строк прошлыми записями, оставив
   будущие за пределами ответа. Теперь выдача сортируется как:
   будущие даты по возрастанию → прошлые по убыванию.
2. **Страница родителя:** отдельные разделы «Ближайшие занятия»
   и «История посещений». Будущие занятия расположены по времени,
   старые посещения — от новых к старым.
3. **Регрессия:** `scripts/dance-owner-contract.test.mjs` содержит
   контрактные проверки нового порядка, разделения списков, статуса
   сверки денег и семейной привязки абонемента.

## Важные требования для сценария 2 филиалов

### Персонал
52 тренера могут быть ресурсами, но только приглашённые сотрудники
имеют доступ к своему логину. Владелец должен отдельно подтвердить
услуги тренера, ставку, смены, филиал, доступ к занятиям.
Увольнение — архивирование после переназначения будущих уроков;
история начислений, посещений и согласований остаётся.

### Залы
В филиале А большой зал используется для групп, два малых —
для аренды. Арендная плата собственнику (расход) и сдача малых залов
клиентам (доход/обязательство) — **разные операции**. Одна и та же
комната не должна одновременно резервироваться для тренировки и
платной аренды.

### Абонементы
10 посещений за 7000 ₽ создают право на 10 занятий после
подтверждённой активации. Денежное поступление и признание
реализации занятий — разные значения; при возврате абонемента
учитываются уже использованные посещения. 700 ₽ — условная
стоимость посещения при полном использовании пакета, а не
автоматически доказанная чистая прибыль.

### Финансы
Из входных данных известны 3 млн ₽ месячного оборота,
700 тыс. ₽ аренды залов первого филиала, 100 тыс. ₽ окладов
двух менеджеров. **2,2 млн ₽ — только арифметический остаток до
зарплат тренеров, аренды филиала Б, налогов, страховых
взносов, маркетинга, эквайринга и прочих затрат; это не прибыль.**
Налоговые обязательства нельзя вычислять из выдуманной
организационно-правовой формы.

## Проверка и статус

В этом сеансе изменены исходники родительского кабинета и
контрактный тест в `main`; запуск PostgreSQL, Jest, Playwright,
платежей/кассы и полная сборка не подтверждены.
Статус промышленного запуска: **NO-GO до живого E2E**.

Следующее направление разработки:
- единая карточка урока с участниками, абонементами,
  задолженностью и действиями по каждой персоне;
- сквозные возвраты и сверка оплаты без выдуманных статусов;
- контроль занятости сдаваемых залов и недопущение двойного бронирования;
- SQL-оптимизация недельного расписания 52+ тренеров и филиальные права.
