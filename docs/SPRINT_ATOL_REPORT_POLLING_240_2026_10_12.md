# Sprint 240 — автоматическая сверка чеков АТОЛ через GET report

Дата: 12 октября 2026. Ветка: main. CI/GitHub Actions не добавлялись.

## Реализовано в исходниках

1. Миграция `infrastructure/postgres/240_atol_fiscal_reconciliation_queue.sql`:
   отдельная долговечная очередь задач на чтение статуса фискальных
   документов, tenant RLS, уникальность документа, защита от
   параллельных обработчиков PostgreSQL `FOR UPDATE SKIP LOCKED`,
   lease на 120 секунд и backfill ранее отправленных чеков с UUID.
2. `AtolReceiptsService`:
   - создание задания при получении от АТОЛ UUID для операций
     `sell` (аванс), `sell_full_payment` (зачёт аванса) и
     `sell_refund` (возврат);
   - **только GET `report/{uuid}`**, новые `POST sell` и
     `POST sell_refund` фоновый обработчик не создаёт;
   - проверка UUID, `external_id`, суммы, ФН, ФД, ФП через
     прежний процесс ручной сверки; финансовый ledger повторно
     не проводится;
   - при WAIT повторять GET с паузой, при DONE/FAIL закрывать задачу,
     при ошибке провайдера — ограниченная экспоненциальная задержка;
     после 80 попыток задача становится `EXHAUSTED` и требует
     вмешательства оператора;
   - ошибки в журнале не содержат ответов провайдера, токенов,
     адресов клиентов и фискальных документов;
   - флаг включения отдельный, по умолчанию false.
3. `GET /api/v1/provider-connectors/sites/:siteId/atol/report-health`:
   агрегированные состояния очереди, число документов без
   провайдерского UUID, отсутствие доступа сотрудников без
   `sites.manage` на всю организацию.
4. UI: `/app/settings/integrations/connect` показывает
   доступность автоопроса, состояния и необходимость ручной сверки.
5. Jest: `atol-report-poll.spec.ts`; source gate контролирует
   приоритет безопасности `GET only`, lease, RLS, уникальность.

## Важный отказобезопасный сценарий

Если HTTP `POST sell` был принят, но соединение пропало до
получения UUID, создаётся `UNKNOWN` без UUID. **Никаких новых
POST и автоматических повторов.** Оператор сверяет документ
по `external_id` в кабинете АТОЛ, получает фактический UUID,
выполняет существующую ручную проверку. Когда известны внешний
идентификатор и статус WAIT, работа продолжается очередью GET.

Если worker/сервер падает после получения задачи, lease
истекает через 120 секунд, после чего другой экземпляр API
может повторить безопасный GET.

## Конфигурация

Все флаги **по умолчанию выключены**:

```dotenv
COREBIZ_ATOL_RECEIPTS_ENABLED=false
COREBIZ_ATOL_PRODUCTION_RECEIPTS_ENABLED=false
COREBIZ_ATOL_REPORT_POLL_ENABLED=false
COREBIZ_ATOL_REPORT_POLL_INTERVAL_MS=60000
```

После резервного копирования и успешного применения миграций
`234..240` на **staging**, проверки реальных тестовых чеков
и фискальных отчётов можно включить только:
`COREBIZ_ATOL_REPORT_POLL_ENABLED=true`.

Флаг фонового чтения не включает отправку чеков. Тестировать
`COREBIZ_ATOL_RECEIPTS_ENABLED=true` разрешается отдельно
только с тестовым АТОЛ и тестовым банком. В production
`COREBIZ_ATOL_PRODUCTION_RECEIPTS_ENABLED` оставлять
false до выполнения бухгалтерской и операционной приёмки.

Не включать polling до миграции 240: без очереди будут
ошибки обращения к отсутствующей таблице/функции.
Значение частоты — целое число от 30000 до 300000 мс.

## Тестовый выпуск

```bash
git checkout main && git pull --ff-only origin main
corepack enable && pnpm install --frozen-lockfile
pnpm db:migrate
pnpm typecheck && pnpm test && pnpm build && pnpm stability:check
```

После успешного запуска на тестовой БД сделать read-only
аудит `scripts/atol_fiscal_recovery_audit.sql`
под tenant-scoped сессией.

Критические E2E:
- касса отвечает WAIT → DONE с ФН/ФД/ФП, сумма совпадает;
- один и тот же webhook + повтор GET не создаёт второй чек;
- провайдер не работает час, после восстановления следующий
  GET подтверждает исходный документ, без повторного POST;
- перезапуск нескольких API одновременно не дублирует GET
  с lease; завершение операции безопасно при гонке с ручной сверкой;
- оператор вручную устанавливает UUID для UNKNOWN с
  корректной внешней идентичностью; чужой UUID отклоняется;
- когда документ FAIL, необходима **ручная процедура**;
  автоматическое создание нового документа не разрешено;
- отчёт принадлежит точному tenant и сайту;
- деньги в Finance и кассовые чеки не перепутаны.

## Что пока не завершено

- Выпуск ФФД 1.2 для товаров с обязательной маркировкой,
  коды идентификации, Честный ЗНАК/ГИС МТ и ЭДО.
- Чеки коррекции, частичные возвраты, сложный НДС по строкам
  (пока ставка одна для пилота), автоматический алерт в почту
  для exhausted задачи.
- Приёмочные испытания с реальными кассами/банком на сервере.
- Проверенный recovery без UUID у АТОЛ; фискальный POST
  в таких случаях запрещён до сверки.
- Отказоустойчивость 99,99% не доказана: нужен production
  monitoring, замеры latency, восстановление из backup и
  подтверждение провайдерского SLA.

Это реализация в исходниках, а не сертификат эксплуатации
или подтверждение требований 54-ФЗ.
