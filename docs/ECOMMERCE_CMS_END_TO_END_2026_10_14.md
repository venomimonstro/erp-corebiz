# CoreBiz · Единый интернет-магазин и внутренняя CMS
Дата: 14 октября 2026
Статус: изменения сохранены в GitHub main; промышленный запуск НЕ подтверждён.

## 1. Что получает владелец
После регистрации и выбора ECOMMERCE_STORE:
1. **/app/start** — выбор ниши и настройка компании.
2. **/app/commerce/launch** — главное рабочее место запуска магазина.
3. **/app/catalog/products** — один каталог: товар, карточка, вариант, SKU, цена, закупочная себестоимость, изображения.
4. **/app/inventory/stock** — склады, приход, движения, страховой запас, доступный остаток с учётом резервов.
5. **/app/sites** — CMS: главная страница, блоки, каталог, SEO, публикация, публичный адрес/свой домен.
6. **/app/sites/payments** — собственные платежи, касса и методы выдачи/доставки.
7. **/app/sales/orders** и **/app/oms** — поступление заказов, подтверждение, складской резерв, комплектация, отгрузка.
8. **/app/returns**, **/app/finance**, **/app/commerce** — возвраты, деньги и пополнение запасов.

Владелец создает CMS-магазин через обычную форму в интерфейсе. При выборе STORE сервер в одной транзакции создает site, страницу HOME, черновик, блок PRODUCT_GRID и storefront_config. Новый магазин не требует второй базы продуктов; публичный каталог получает цены из sku и доступный остаток из inventory_balance/inventory_policy.

**Канонический конструктор:** SitesModule/SitesService + StorefrontService обслуживают /api/v1/sites, публичные страницы и checkout. Отдельный старый SiteBuilderModule присутствует в исходниках, но не импортируется в AppModule и НЕ должен превращаться в еще один торговый каталог без миграционного решения.

## 2. Новое рабочее место /app/commerce/launch
* Позволяет создать сайт STORE, выбрать существующий сайт, открыть CMS, настроить оплату/доставку и перейти на публичную витрину.
* Берёт реальные статусы из GET /sites, GET /storefront/site/:siteId/readiness, GET /dashboard/commerce, GET /go-live/readiness.
* Каждая из 9 проверок сайта ведёт на экран, где проблема исправляется.
* Ошибка любого API сбрасывает соответствующее прежнее состояние; зелёного «готово» при неизвестном статусе нет.
* Не смешивает «готов к тестовым заказам» с разрешением принимать реальные деньги.
* Создание сайта при сетевом timeout не отправляется автоматически повторно; владелец видит предупреждение проверить список.
* Доступ сохраняется по RBAC sites.read/sites.manage и существующим возможностям tenant.

## 3. Проверяемая последовательность от имени владельца
**А. Регистрация:** создать компанию, выбрать ECOMMERCE_STORE. Отказ: неверный e-mail/неподтверждённый профиль, без второго tenant.
**Б. Товар:** создать два STOCKABLE SKU, цены и себестоимость. Отказ: пустая цена/невалидные данные.
**В. Склад:** открыть warehouse, внести документ движения +3000 milli на SKU. Отказ: неверное количество/повтор idempotencyKey. Доступно физическое − резерв − страховой запас.
**Г. CMS:** создать STORE. Сервер одной транзакцией создаёт витрину и PRODUCT_GRID; страница остаётся черновиком. Отказ: занят publicSlug, ошибка сети; не клонировать магазин.
**Д. Публикация:** проверить страницу редактором, явно опубликовать. До публикации HOME_PUBLISHED=false; каталог не считается опубликованным.
**Е. Получение:** создать PICKUP/LOCAL_COURIER. Без выбранного действительного способа заказ не подтверждается.
**Ж. Корзина:** внешний клиент читает публичный каталог, добавляет товар, отправляет checkout. Сервер записывает заказ через **SalesService.create** с идемпотентностью storefront:cart:<id>.
**З. Повтор checkout:** второй запрос по той же корзине возвращает один заказ OMS, не создает второй.
**И. Резерв и backorder:** товар резервируется в том же учёте склада или недопоставка обозначается явно; нельзя выдавать обещание доставки неподтверждённого SKU.
**К. Деньги:** подтверждённый заказ ещё не означает оплату. Требуются внешний PSP webhook, финансовый ledger, KKT/ОФД и возвраты.
**Л. Заказ/возврат:** отгрузка/самовывоз и возврат связаны с исходными заказом, оплатой и складом.
**М. Управление:** владелец видит необработанные заказы, проверки оплаты, открытые закупки и риск нехватки без повторного ввода SKU.

## 4. Исправленные риски
- `StorefrontService.readiness` не выставляет canTestOrders=true при отсутствии хотя бы одной активной доставки или самовывоза. Ранее проверялись только пять первых условий (сайт, HOME, каталог, цена, остаток).
- UI создания CMS-магазина больше не вызывает window.prompt, позволяет предварительно ввести название и адрес, а при таймауте сохраняет видимую неопределённость.
- После создания нового сайта обновление списка больше не переключает владельца на старый первый сайт из-за устаревшего closure.
- Полная продакшен-готовность всегда требует `canLaunchWithOnlinePayments` от сервера И актуального `go-live/readiness.ready`. На текущем сервере `canLaunchWithOnlinePayments=false` до настоящих провайдерских проверок.

## 6. Команды для отдельного тестового окружения
```bash
git checkout main && git pull --ff-only origin main
pnpm test:ecommerce:contract
pnpm typecheck && pnpm test && pnpm build
```

Только на **свежем localhost API, направленном в уничтожаемые PostgreSQL и Redis**, с последним набором миграций:
```bash
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_BASE_URL=http://127.0.0.1:4000 \
COREBIZ_SMOKE_WEB_ORIGIN=http://localhost:3000 \
pnpm test:ecommerce:owner
```
НЕЛЬЗЯ запускать на рабочей базе. Сценарий создает пользователя, товары, склад, сайт, публичный заказ и резервы. Учитывайте rate limiting регистрации — отдельный тестовый Redis или очистка только тестовой среды.

## 7. Дальнейший release gate
P0: рабочая проверка каждой операции по цепочке; PSP→ledger→KKT/ОФД→возврат; живой test-domain HTTPS/SEO; одноразовый double checkout на последнем SKU; sandbox СДЭК/Почты; RLS двух арендаторов; backup/restore.
