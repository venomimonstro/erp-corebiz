# CoreBiz ERP: бизнес-процессы, границы модулей, безопасность и масштабирование
**Дата:** 2026-10-11. **Статус:** архитектурный контракт и кодовый аудит; НЕ заключение о пройденном пентесте или нагрузке.

## 1. Принцип построения
CoreBiz — одна многопользовательская ERP-платформа с отраслевыми профилями, а не несколько самостоятельных баз. Одна организация выбирает вертикаль и включает необходимые возможности. Внутри неё есть юридические лица, филиалы, склады, ресурсы, сотрудники, клиенты и собственные справочники. Между различными арендаторами SaaS действует строгая граница `tenant_id`. Между филиалами и юридическими лицами ОДНОГО арендатора RLS tenant не создаёт автоматической изоляции: там необходим отдельный ABAC/scope.

Базовые источники истины:
- `party`/CRM: контрагент, лид, сделка и история контактов; сотрудники отвечают за свои лиды.
- `catalog`, `product_variant`, `sku`: единый товар/услуга и единый SKU внутри tenant; SKU у маркетплейса — внешняя привязка, а не новый физический товар.
- `service_booking` и отраслевые операционные сущности: занятый слот, специалист, рабочее место; один слот нельзя продавать дважды.
- `sales_order` и `oms_order`: заказ клиента и последующее распределение исполнения.
- `inventory_balance`, складские проводки, WMS: физический остаток и резервы; не редактировать баланс непосредственно извне.
- `financial_obligation`, `finance_invoice`, `payment`: денежные обязательства, счета, фактическая оплата; оплата не равна выручке.
- Бухгалтерские регистры и зарплатные ведомости: отражение фактов после проверки, статусы согласования и закрытые периоды.
- `task`, проекты, audit_event, outbox: ответственность за процессы, аудируемый журнал и асинхронные уведомления/интеграции.

Каждая команда проходит маршрут: проверка сессии → capability + RBAC/ABAC → TenantContext → RLS → проверка бизнес-инвариантов и версии → атомарная транзакция → событие/outbox → воркер с идемпотентностью → отчёт/уведомление. Сайд-эффекты у внешних провайдеров всегда требуют retries, dead-letter и сверки с провайдером: «exactly once» для удалённых API не гарантируется.

## 2. Общая сквозная логика
1. Подключение: владелец создаёт tenant, выбирает отрасль, юридическое лицо/филиалы, приглашает пользователей. Должны применяться права и готовность интеграций. Ошибка этапа НЕ должна активировать фиктивно готовый процесс.
2. CRM: обращение с сайта/телефона/мессенджера → клиент/сделка → задача сотруднику → согласованное предложение. Дедупликация контактов и уникальные external event IDs.
3. Коммерческая операция: сделка → заказ, запись, заказ-наряд или проект. Все ссылки содержат tenant, проверяются owner/branch/ответственные/статус. Отсутствие цены или договора не подменяется нулём.
4. Исполнение: OMS/WMS резервирует товар, сервис блокирует зал/мастера, проект фиксирует задачи и часы; при неудаче возвращает состояние либо ставит процесс в явный WAITING/REVIEW.
5. Деньги: счет и обязательство → эквайринг/банк → сопоставление фактической оплаты → задолженность/переплата/возврат; финансовая операция с внешним ID не повторяется.
6. Себестоимость: материалы, закупочные цены, часы, ставки, аренда и комиссия каналов. Снимки в момент исполнения; смена текущих ставок не переписывает закрытый период.
7. Бухгалтерия/налоги РФ: документ → черновик проводок → проверка реквизитов → подтверждение → календарь деклараций и налогов. Автоматическая отправка только при реально подключённом, юридически поддерживаемом операторе; остальное явно «проверить вручную».
8. Контроль владельца: единый Action Queue формируется из фактов и SLA; не закрывать исключение простым скрытием карточки. Все коррекции финансов требуют основания, разрешения и audit_event.

## 3. Отраслевые процессы (фактические профили в business-verticals.ts)

| Розница | товары → закупка → приёмка → склад/полка → продажа → оплата → возврат → прибыль по точкам | отрицательный доступный остаток, повторное списание |
| Опт B2B | контрагент → коммерческие условия → КП → заказ → лимит дебиторки → резерв → отгрузка → УПД/счет → оплата | превышение лимита, чужие цены, отгрузка без резервов |
| Интернет-магазин | каталог → витрина/корзина → order → OMS → резерв → WMS pick/pack → отправка → платёж/возврат → атрибуция каналов | duplicate checkout, oversell, отмена при уже отгруженном заказе |

Последовательности описывают целевой единый UX и точки интеграции; факт наличия шаблона вертикали не означает автоматически подтверждённую производственную готовность всех операций.

## 4. Модули и интеграционные границы
- **Платформа:** auth, membership, tenant, roles, capabilities, branches и audit. Владелец может включить CRM+маркетплейсы, не подключая WMS; frontend скрывает неактивные элементы, backend отклоняет вызовы.
- **Операции:** CRM, каталог, продажи, OMS, закупки, WMS, сервисные записи, танцевальные группы, проекты. Один источник каждой операции, сквозной ID и idempotency key для повторяемых команд.
- **Финансы:** обязательства, платежи, банковская сверка, счета, себестоимость, payroll, бухгалтерия РФ. Финансовые поля имеют отдельные разрешения, включая cost/margin/finance; связанные семейные плательщики и зарплаты не раскрываются тренеру.
- **Автоматизация:** outbox с транзакционной записью, воркеры `FOR UPDATE SKIP LOCKED`, leases, retries, DLQ/контроль ошибочных задач; внешний API вызывается вне длинной транзакции БД, результат подтверждается и сверяется.
- **Маркетинг:** данные Яндекс/ВК/сквозной аналитики присоединяются к сделке и фактическому заказу; агрегаты не должны изменять первичные платежи.
- **Интерфейсы:** одна стартовая панель по роли, отраслевой onboarding, поиск по доступным объектам, журнал исключений, постепенное раскрытие сложных финансовых разделов.

## 5. Модель безопасности и результаты кодового аудита
За основу приняты OWASP ASVS 5.0, в частности V8: разрешения на функцию, объект, поле и tenant проверяются на доверенной стороне API. Уже есть:
- Argon2id и непрозрачный HttpOnly session cookie, проверка Origin для изменяющих браузерных запросов, CORS по `WEB_ORIGIN`, ограничение размера запросов и глобальный rate limit.
- `TenantContext` из разрешённой сессии, `set_config('app.tenant_id', ...,true)` в транзакции и RLS на множестве таблиц.
- Scoped roles, журнал аудита, защита некоторых финансовых документов и складских переходов на уровне SQL.
- Исправления 2026-10-11: скрытие закупочной стоимости без финансового разрешения, ограниченный page API, лимиты пула БД и новая диагностика роли/RLS.

**Риски, требующие внешней проверки и дальнейших исправлений:**
1. **P0:** Если API подключается к PostgreSQL как SUPERUSER, BYPASSRLS или owner не-FORCE-RLS таблиц, приложение теряет вторую линию изоляции. На production проверить `scripts/security_tenant_isolation_gate.sql` *под реальной runtime-ролью*.
2. **P0:** Проверить минимум два арендатора и несколько филиалов одного арендатора: запрет чужих документов, файлов, search, export, фоновых задач и linked UUID. Изоляция филиалов внутри tenant требует ABAC; одного `tenant_id` недостаточно.
3. **P0:** Пентест критичных публичных endpoints и интеграций: проверки подписи/секретов вебхуков, replay protection и idempotency; безопасность файлов, SSRF по URL, IDOR, CSRF и SQL injection. Кодовый просмотр не является пентестом.
4. **P0:** Отдельная БД-роль для миграций и приложения, отсутствие schema ownership/runtime SUPERUSER. Минимизировать доступ SECURITY DEFINER: `PUBLIC EXECUTE` и search_path должны проходить ревью.
5. **P1:** Sensitive mutation: изменение банка, ролей, массовый export, возврат, закрытие учётного периода — step-up/разрешение второго лица для крупных сумм; журнал неизменяемый и детекция необычных действий.
6. **P1:** Нет доказанного восстановления из резервной копии, секрет-сканирования, SAST/DAST/SCA и оценки зависимостей после каждого релиза. Без этого «защищена от взломов» нельзя подтверждать.
7. **P1:** Доступ к API и frontend не заменяет field-level security: себестоимость, ФИО плательщика, зарплата, маржа, паспортные/налоговые поля проверяются на уровне SQL/API.
8. **P1:** 22 MB JSON body может давать высокий RAM пик; массовый импорт необходимо осуществлять через streaming-объектное хранилище и ограниченный воркер, а не прямой POST большого массива.
9. **P1:** Rate-limits для тяжёлых операций и очереди должны fail-closed при отказе общего Redis и не сводиться к IP клиента. Разбор секретов из логов/ошибок и срока хранения обязателен.

## 6. Права доступа по ролям
| Роль | Читает / изменяет | Не должна видеть |
|---|---|---|
| Владелец организации | Все разрешённые данные своего tenant, назначает роли, подтверждает закрытия | другие tenants |
| Администратор филиала | записи, отгрузки, сотрудники и клиенты своего branch, в рамках предоставленного ABAC | банковские реквизиты/чужие филиалы без отдельного права |
| Менеджер продаж | лиды, сделки, свои заказы, клиентские цены | закупочную себестоимость, зарплаты и налоги |
| Мастер/тренер | свой график, состав своих занятий, посещаемость; *свою* ведомость | полную зарплатную ведомость, скидки других, данные плательщиков |
| Кладовщик | свой склад, задачи WMS, штрихкоды, физические количества | счета, платежи, маржинальность |
| Финансист/бухгалтер | счета, сверку, обязательства, учёт, cost/margin при разрешении | право приглашать админов по умолчанию |
| 3PL-поклажедатель | только свой owner stock + свои акты, счета и отгрузки в пределах scoped portal | товары других владельцев внутри общего склада |
| Клиентский портал | адресно делегированные документы и собственные согласования | сотрудники, иные сделки, другие клиенты |

`is_owner` и role permission не должны обходить проверку tenant. Поддержка имеет временный делегированный read-only доступ, событие выдачи прав логируется.

## 7. 1 000 одновременных пользователей: архитектура и проверка
**Важно:** 1 000 авторизованных открытых браузеров ≠ 1 000 одновременно выполняемых SQL-транзакций и ≠ 1 000 RPS.

Целевая схема: несколько stateless NestJS API + Next.js за балансировщиком; Redis для rate limits/semaphores/коротких кэшей; отдельный набор worker replicas для outbox/marketplace/import; PostgreSQL 17 c WAL backups и проверенными PITR, отдельный runtime DB user; PgBouncer transaction mode для распределения коротких транзакций, плюс отдельная миграционная DB роль. Файлы — внешнее приватное хранилище с короткоживущими разрешениями.

**Недавние изменения:** API DB pool ограничен `COREBIZ_DB_POOL_MAX` (10 по умолчанию, диапазон 2–40), время получения соединения 3 s, SQL statement timeout 30 s. Общий пул = число реплик × максимум соединений; например 6 × 10 = 60 без учёта воркеров/администрирования. Установка `max=1000` на каждую реплику запрещена как анти-паттерн.

Приёмочные пороги **для проверки, не подтверждённые факты:** тест `scripts/load-1000-sessions.mjs` на одноразовом стенде и 1 000 уникальных сессий, p95 не более 1 500 мс, доля ошибок не более 0,5%, отсутствуют HTTP 500/502 и потеря бизнес-инвариантов. Отдельно — 15 мин steady-state, 60 мин soak, отказ Redis/одной API-реплики/worker, восстановление Postgres из backup, нагрузка 1000 конкурентных операций резерва. Все результаты должны сопровождаться host CPU/RAM, активными PG connections, locks, slow queries, очередями и lag.

## 8. Один миллион SKU у одного клиента
- Клиентский UI **никогда** не получает миллион записей: keyset pagination и серверный поиск с максимум 200 SKU/страницу, выдача без полного `COUNT(*)`; отдельный экспорт в фоновой задаче.
- `GET /api/v1/catalog/products/page?limit=100&cursor=<uuid>&q=<text>`; в ответе `items`, `nextCursor`, `hasMore`. Исходный legacy список до 1 000 SKU остаётся ради совместимости, но другие экраны также нужно переводить на ленивую подгрузку.
- Индексы: `sku(tenant_id,id)` для page и `pg_trgm` GIN для substring-поиска SKU/штрихкода/названия. Миграция 222; на уже больших таблицах заранее планировать создание аналогичных индексов `CONCURRENTLY` во внепиковое время, потому что обычная миграция может блокировать запись.
- Импорт миллионов SKU: chunk 1–5 тыс., проверка tenant+SKU+barcode, staging и dead-letter ошибок строк, идемпотентный upsert, версия прайса, контроль квоты/прогресса и отмена. Не строить мегатранзакцию и не держать массив в RAM.
- OMS/WMS: индексы по (tenant,sku,warehouse,state), атомарное резервирование под блокировкой конкретного SKU/склада; горячие склады — партиционирование ledger по времени/tenant лишь после измерений, не преждевременно.
- Маркетплейсы: учитываются confirmed physical stock, reserved, shadow demand, safety, remote published; увеличение остатка другого канала только после подтверждения предыдущего уменьшения.
- Рост до >1 млн SKU сам по себе не требует шардирования. Сначала EXPLAIN ANALYZE, профилирование больших tenants, реплики только для необязательных чтений с контролем lag, затем выделение тяжёлых tenants/партиционирование при доказанной необходимости.

## 9. Release gate: обязательные доказательства
1. `pnpm --filter @corebiz/api typecheck && pnpm --filter @corebiz/api test --runInBand && pnpm build`.
2. Миграции на **копии** prod, backup/PITR и rollback/runbook. Не мигрировать продакшен без предварительной оценки времени создания индексов.
3. `psql "$RUNTIME_DATABASE_URL" -v ON_ERROR_STOP=1 -f scripts/security_tenant_isolation_gate.sql`, именно non-owner, NOBYPASSRLS.
4. A/B tenant matrix: 20 ресурсов из разных вертикалей, GET/POST/PUT/DELETE/search/export/webhook/worker; никакой информации другого tenant, проверка филиалов и специализированных внешних порталов.
5. Двойные оплаты, заказы и складские резервы при конкурентной нагрузке; никаких отрицательных ATP или дублей счетов и проводок.
6. Локальный load gate на 1 000 независимых сессий и отдельно 1 млн тестовых SKU, со свежими EXPLAIN, графиками p95/p99, CPU, WAL, locks, соединения и Redis/worker backlog.
7. Наблюдаемость и реагирование: trace IDs без секретов, алерты на backlog, 5xx, повторные платежи, слишком долгие locks, brute force и попытки IDOR; восстановление из backup проверено на отдельной БД.

**Релизный вердикт на момент документа:** часть защит присутствует и часть дефектов исправлена в main, но нет показанных успешных результатов DAST/пентеста, live tenant-isolation проверки и 1 000 одновременных сессий / 1 млн SKU на наполненной БД. Коммерческая готовность этих требований — НЕ ПОДТВЕРЖДЕНА.


## 10. Следующее усиление платформы (продолжение 2026-10-11)

Реальные изменения в коде этого этапа:

- **Каталог / прибыль по товару:** для записи ненулевой закупочной стоимости через `POST /catalog/products` проверяется `finance.read` или `catalog.cost.read` с эффективным scope `all`. Одного `catalog.write` недостаточно. Цена валидируется до SQL, в том числе верхние границы PostgreSQL `bigint`; покрыто регрессионными тестами.
- **Redis rate limits:** `INCR` и установка TTL выполняются одной Lua-операцией. Даже разрыв между двумя Redis-командами не должен оставлять бессрочный ключ блокировки. Потеря Redis по-прежнему не должна обходить ограничение.
- **PostgreSQL:** API-транзакции используют локальные `lock_timeout = 5s` и `idle_in_transaction_session_timeout = 60s`. Это защита от длительного удержания блокировок, **не** увеличение пропускной способности автоматически. Порог проверять на длинных бухгалтерских операциях.
- **Хаб маркетплейсов:** выбор SKU теперь использует `GET /catalog/products/page` и адресный `GET /channels/stock-hub/mappings`; выдача не более 50–100 элементов, связь `tenant_id + connection_id` в SQL. Индексы миграции `224_marketplace_million_offer_lookup.sql` для внешних артикулов; первичный обзор ограничен 200 витринами, а полный экспорт требует фонового задания.
- **Агрегаты большого клиента:** обзор не пересчитывает `count(DISTINCT sku_id)` по всему складу при каждом открытии интерфейса. Число ожидающих пересчёта пулов ограничено подсчётом до 10 001, то есть это насыщенный индикатор, а не точная бухгалтерская цифра.

Оставшиеся **обязательные до коммерческого SLA** проверки и задачи:
1. Проверить на стенде одновременно 1 000 различных пользовательских сессий, отдельно нагрузку на записи/резервы и 1 млн SKU; сохранить p95/p99, throughput, locks, WAL, memory, Redis/PgBouncer и точный профиль запросов.
2. Провести реальное тестирование runtime-role против tenant RLS, включая SECURITY DEFINER, загруженные файлы, поисковые индексы, webhook/worker, branch scope, внешние 3PL/клиентские порталы.
3. Выполнить регрессию отложенных платежей, массовых документов и длительных расчётов с новыми лимитами ожидания транзакций; при необходимости разбивать длинные операции на идемпотентные задачи.
4. Реализовать фоновые CSV/XLSX импорты/экспорты миллионов позиций через staging, ограниченную очередь и streaming; старый короткий список SKU не является интерфейсом массового обмена.
5. Замерить стоимость индексов `222` и `224` **на копии реальной базы**; на заполненном миллионами строк production-стенде применять `CREATE INDEX CONCURRENTLY` по утверждённому отдельному плану без транзакции мигратора.

**Фактический статус:** изменения зафиксированы в исходном коде. Сборка, DB-миграции, пентест, 1 000 сессий и 1 млн SKU в текущей сессии не были выполнены, поэтому заявлять production-ready или доказанную устойчивость нельзя.


## 10. Устранение RBAC-эскалации, проверка и границы гарантий (11.10.2026)

Для каждой вертикали один и тот же разрешительный путь применяется **до** чтения конфиденциальных данных и **перед** финансовыми/складскими изменениями:

- `AuthorizationService.resolveScope` использует детерминированную агрегацию ролей и **уважает реальный scope** разрешения `*`: `own` не становится `all`. Проверяются соответствие `membership.user_id` активной сессии и `membership.status='ACTIVE'`.
- `RolesService` требует `roles.manage` в масштабе всей компании (`all`) как на чтение конфигурации ролей, так и на назначение. Администратор не вправе назначать полномочия шире собственных. Роль `OWNER` не может создаваться простым назначением сотруднику с `is_owner=false`.
- Миграция `223_rbac_owner_escalation_guard.sql` проверяет инвариант на уровне PostgreSQL. Несанкционированные уже существующие назначения `OWNER` к не-владельцам удаляются. Перед применением к production необходимо убедиться, что неформально назначенные «со-владельцы» были корректно юридически оформлены как владельцы.
- `scripts/security_rbac_owner_gate.sql` запускается при проверке релиза **после** миграций вместе с проверками RLS и привилегий `SECURITY DEFINER`. Восстановление миграционного реестра проверяет действительную таблицу `schema_migration`, не `schema_migrations`.

**Важное ограничение текущего scope-представления:** `team` и `branch` не являются математически вложенными наборами сотрудников; при одновременных ролях в коде выбирается наиболее широкий ранг. Для сложных организаций необходимо моделировать эффективный доступ к объекту как объединение допустимых наборов сотрудников/филиалов, а не только одно enum-значение. До подтверждения такого ABAC не следует выдавать сотрудникам противоречащие друг другу `team` и `branch` scope на одну чувствительную функцию.

**Текущие проверки, а не обещания:** тесты RBAC и изоляции включены в исходники, но нагрузка **1000 одновременно активных клиентов** и **миллион SKU** не подтверждены успешными результатами реального стенда. Операционная готовность требует запуска на наполненной одноразовой БД `scripts/load-1000-sessions.mjs`, проверки p95/p99, RLS-матрицы двух tenant, `EXPLAIN (ANALYZE, BUFFERS)` каталогов, 60-минутного soak, конкурирующих резервов и восстановления после отказов Redis/PostgreSQL.


## 11. Экспорт больших организаций: эксплуатационные ограничения

Новая реализация `apps/worker/src/tenant-export.ts` обходит строки постранично, записывает JSON/CSV в поток `gzip` без накопления всего исходного набора в heap и использует `REPEATABLE READ, READ ONLY` в tenant-контексте. Для таблиц с `id` используется keyset по первичному ключу; `inventory_balance` (без одиночного `id`) использует составной ключ `(tenant_id,warehouse_id,sku_id)`. Для менее крупных legacy-таблиц без известного ключа остаётся `OFFSET`, это явный кандидат на следующий рефакторинг.

CSV нейтрализует пользовательские формулы (префиксы `=`, `+`, `-`, `@` с ведущими управляющими символами). Потоки ограничены `MAX_RAW_BYTES=200 МиБ`, `MAX_ARTIFACT_BYTES=100 МиБ`; файл сохраняется в `bytea` PostgreSQL с семидневным TTL. Ограничения — защита от OOM, **не** обещание, что tenant с миллионом полных товарных карточек поместится в один экспорт. Для таких организаций нужен разбиваемый на несколько файлов архив в защищённом объектном хранилище, с потоковой выдачей и подписью разовых ссылок; лимит `bytea` и RAM нельзя просто увеличивать.

Проверки: `pnpm --filter @corebiz/worker test` и `pnpm --filter @corebiz/worker typecheck`. Отдельно требуется интеграционный прогон на PostgreSQL: в одной организации 1 млн SKU, 1 млн складских балансов и десятки тысяч документов; в другой — независимые данные. Проверить хеши файлов, `entityCounts`, восстановление JSON, очистку секретов, 1 000 одновременных сессий API, p95/p99 и деградацию при падении Redis/worker. Эти измерения пока **не подтверждены**.

Релизный порядок: сначала обновить код, затем выполнить тесты, проверить резервную копию базы и только затем включать экспорт на больших тенантах. Если экспорт не проходит по лимиту — задание должно завершиться контролируемой ошибкой, а не опустошать heap и не мешать операциям других клиентов.
