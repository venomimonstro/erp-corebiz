## Реализовано в этом этапе

### 1. Полнокаталожный поиск, фильтрация и пагинация WMS

Ранее `/app/wms/operations` запрашивал первые 500 SKU, а поиск и фильтрацию делал локально — могла быть пропущена нехватка на SKU №501 и далее.

- Новый API: `GET /api/v1/wms/operations/warehouses/:warehouseId/stock-page`, параметры `query`, `onlyProblems`, `limit` (10–100), `cursor`.
- RBAC: `wms.read`, SQL строго `tenant_id` + `warehouse_id`.
- Базовый ответ: `items, nextCursor, hasMore, stockSource, inboundSource, stableSnapshot:false`.
- Выборка сортируется по имени товара, коду SKU, id SKU. Курсор содержит warehouse + фильтры; нельзя менять фильтр и использовать старую страницу.
- UI: поиск выполняется в PostgreSQL по всему складу; кнопка «Показать следующие 100 SKU»; прежний read-only маршрут волнового подбора сохранён.
- Сводные численные показатели на загруженной странице **не объявляются** показателями всего склада.
- При изменении данных между страницами возможен неповторяемый снимок: `stableSnapshot:false`. Для юридически значимых отчётов необходим отдельный snapshot/reporting контур.

### 2. Ожидаемая поставка по реальному складу назначения

- В `inventory.replenishment` и обоих WMS view теперь выбирается `po.destination_warehouse_id`, если он заполнен.
- Для старых PO без явного склада допускается только однозначный `destination_branch_id`, у которого ровно один активный склад.
- Неопределённое поступление нельзя распределять поровну или «копировать» по всем складам.
- `expected` не увеличивает `physical` или `sellableNow`: физический запас меняется только после проведения приёмки.

### 3. Нулевые остатки и правила пополнения

- В `InventoryService.balances` объединены реальные записи ledger и включённые `inventory_policy`.
- SKU с нулевым физическим остатком, но заданным safety stock, больше не исчезают из отчётов и могут приводить к рекомендации закупки.
- Тот же подход принят в WMS paged view и старом endpoint.
- Отрицательный доступный остаток при избыточном резерве не замалчивается; числа в milli единицах обрабатываются как integer/BigInt.

### 4. Рекомендация → черновик заказа поставщику

В складском центре владелец или закупщик с `procurement.write`:
1. выбирает склад и фильтр «Только дефицит»;
2. видит реальный физический запас, резерв, подтверждённую поставку, рекомендуемое дополнительное количество;
3. выбирает SKU и существующего поставщика;
4. нажимает «Создать черновик закупки»;
5. в существующем `ProcurementService.createOrder` создаётся **DRAFT** c `supplierPartyId`, `destinationWarehouseId`, SKU и рекомендованным количеством;
6. закупщик открывает «Закупки», сверяет цену/количество/условия и отдельно подтверждает заказ; приёмка является самостоятельной операцией.

**Не выполняется автоматически**: списание денег, создание приёмки, изменение физического остатка или подтверждение PO.

После неопределённого ответа POST экран блокирует повтор, пока пользователь не проверит журнал закупок. Для полной серверной надёжности ещё требуется полноценный идемпотентный ключ создания черновика PO.

## Что уже существовало и не было продублировано

- `InventoryService`: единый ledger, резервы, отгрузки, переносы, FIFO, поправки и инвентаризация.
- `ProcurementService`: заказ поставщику, подтверждение, приёмка с идемпотентностью и документами.
- `WmsService`: топология, ячейки, правила размещения, задания putaway/pick/pack/ship, волны, ТСД, пополнение зон, cycle count, SLA, исключения, трудовые KPI, 3PL собственники.
- `WmsInboundService`: ASN, назначение доков, приемка и состояние поставки.
- `WmsOperationsService`: только read-model по единому ledger, без второго склада.

## Оставшиеся блокеры полноценной AXELOT- и МойСклад-зрелости

| Приоритет | Требование | Почему нельзя считать выполненным |
|---|---|---|
| P0 | Серверная идемпотентность создания черновика PO | UI предотвращает двойной клик, но backend ещё не гарантирует защиту при повторе POST после перезагрузки |
| P0 | Контроль качества и карантин **во всём доступном к продаже остатке** | Наличие зоны QUARANTINE не доказывает исключение партий из резервирования/публикации |
| P0 | Live end-to-end order→reserve→pick→ship→fiscal→refund | Исходники и локальные тесты не равны проверенному production потоку |
| P1 | FEFO/серии/срок годности с принудительным сканированием | Требуется полная проверка SKU/lot/серий в атомарной WMS транзакции |
| P1 | Производительное пополнение зон отбора и волны на реальных нагрузках | Нужны 1000+ SKU, 10+ складов и рабочий TSD под сетью с перебоями |
| P1 | Одобренная коррекция инвентаризации с полной историей решений | Код циклической инвентаризации есть, требуется live multi-role/regression |
| P1 | Единая цепочка печатных форм/ЭДО/маркировки/ККТ | Нельзя считать выполненной без сертифицированных и живых интеграций |

**Итог:** клиент получил улучшенный складской рабочий центр и связку «дефицит → черновик закупки» без второго ledger. Полная функциональная эквивалентность МойСклад / AXELOT **не заявляется**.
