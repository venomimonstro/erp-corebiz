# CoreBiz — омниканальная сеть магазинов и CRM

2026-10-11 · реализация в `main`, без GitHub Actions / CI.

## Целевой сценарий: владелец сети электроники

1. Регистрация: выбрать **«Сеть офлайн-магазинов + интернет-магазин»** (`OMNICHANNEL_RETAIL`).
   Автоматически включаются inventory, catalog, sales, OMS, sites, finance,
   accounting, CRM, channels, tasks и прочие функции этого профиля.
2. `/app/start` и `/app/retail`: открыть «Центр», «ТЦ Север» и «ТЦ Юг».
   Создание торговой точки в одной транзакции создаёт `branch`,
   `warehouse` и `retail_location`. Это **отдельные склады** для
   реального учёта. Общий каталог SKU не копируется в каждую точку.
3. Внести товары (например, ноутбуки, телефоны) в `/app/catalog/products`.
   Принять товар в `/app/inventory/stock` или переместить между складами.
   Доступный остаток по точке рассчитывается из `inventory_balance`,
   `inventory_policy`, safety stock и активных резервов.
4. Сотрудник открывает кассовую смену и создаёт заказ на кассе.
   Backend использует canonical `SalesService.create` →
   `SalesService.confirm` → `SalesService.reserve`, на **складе точки**.
   Заказ связывается с физической точкой и каналом. Один повтор запроса
   не создаёт второй заказ; резерв создаётся идемпотентно.
   **Покупка не считается оплаченной или фискализированной!**
5. Для самовывоза оператор `/app/retail` создаёт `CLICK_COLLECT`
   резерв по выбранной точке. Это **ручной сценарий администратора**, не
   автоматическая привязка публичной корзины к магазину.
6. Для интернет-магазина владелец использует существующие
   `/app/sites`, `/app/sites/payments`, OMS и YooKassa. Весь магазин
   работает с тем же каталогом и inventory ledger.
   Аллокация сайта по выбранной физической точке выдачи пока **не**
   закрыта end-to-end; OMS использует собственный поиск складов,
   поэтому точка самовывоза интернет-покупателя не может обещаться
   автоматически до реализации warehouse-locked sourcing.
7. Менеджер видит customer order в `/app/sales/orders`,
   а профильные `retail_order_link` — в `/app/retail`. Для одного
   и того же клиента доступен CRM-контакт. Отдельный терминал эквайринга,
   фискальный чек офлайн, сквозной возврат и маркировка — **открытые P0**.

### Разделы и API

- `/app/retail`: магазины, остатки по точкам, резерв, открытие/закрытие
  смены, перечень заказов.
- `GET/POST /api/v1/retail/locations`
- `GET /api/v1/retail/locations/:id/stock?q=`
- `GET /api/v1/retail/locations/:id/orders`
- `POST /api/v1/retail/orders/reserve`
- `POST /api/v1/retail/locations/:id/shift/open`
- `POST /api/v1/retail/locations/:id/shift/close`
- SQL `231_retail_omnichannel_network.sql`: RLS, отдельные
  branch/warehouse, уникальные idempotency keys и open-shift constraint.
- `retail_cash_shift` — управленческая смена, **не** чек ККТ/ОФД
  и не реестр оплаты. Касса должна отдельно передавать подтверждение.

## CRM уровня amoCRM — реализованные шаги

Изначально в CoreBiz были:
- CRM kanban с drag-and-drop и оптимистическими версиями сделок;
- настраиваемые pipelines/stages, won/lost и причины проигрыша;
- клиент и ответственный, источник/UTM, приоритет/lead score;
- заметки, журнал событий, теги, linked tasks;
- переход из выигранной сделки в Sales Order;
- custom fields и декларативная таблица automation rules.

В этом спринте:
- переключение воронок на UI и создание дополнительных pipeline;
- поиск по карточкам, фильтр забытых сделок/просрочек;
- `POST /api/v1/crm/deals/:id/next-action` создаёт **настоящую**
  связанную задачу, фиксирует `crm_activity`, назначает срок и
  ответственного. Уникальный ключ и fingerprint предотвращают
  повторное создание при сетевом retry;
- `crm.addNote`, `crm.addActivity`, `crm.setDealTags` проверяют
  принадлежность сделки доступной сотруднику области, а не только tenant.
  Это важная защита от доступа продавца к чужой клиентской истории;
- SQL `232_crm_next_action_idempotency.sql` c tenant RLS.

**Что пока не соответствует полнофункциональной amoCRM:**
активное исполнение `crm_automation_rule` по событиям,
омниканальный inbox WhatsApp/TG/телефонии/email, безопасный
OAuth2 обмен и webhooks, автодедуп лидов по телефону, lead
routing/SLA, конструктор триггеров, полноценный
редактор pipeline/stages в UI, отчёты по конверсии и воронке.
Таблица rules есть, но **не следует выдавать её наличие за работающие
автоматизации**.

## Коммерческие P0 — прежде чем продавать как готовую сеть

1. **Публичная online checkout → точка выдачи:** привязка к выбранному
   retail_location и строгая аллокация только из её warehouse.
   При отсутствии полного остатка — fail-closed до платежа.
2. **ККТ/ФН/ОФД 54-ФЗ**: фискальный чек офлайн/онлайн, эквайринг
   терминала, чек полного расчёта при выдаче предоплаты, возвраты.
3. **Розничная оплата**: безопасный POS payment lifecycle
   `AUTHORIZED/CAPTURED/REFUNDED`, reconciliation,
   идемпотентное проведение Finance и закрытие Sales.
4. **Товарные серии**: IMEI/serial, гарантийный талон, сервис,
   серийный номер для возврата, EDI/маркировка по применимости.
5. **Многоточечный P&L**: выручка, комиссионные, себестоимость,
   расходы аренды и зарплат по филиалам, возвраты, KKT shift close.
6. **Боевая CRM automation**: триггеры, очереди сообщений,
   ограничение прав, шаблоны задач и история контакта.
7. **Операционные E2E**: два тенанта, две точки, последний
   экземпляр SKU, два конкурентных заказа, обрыв/повтор HTTP,
   возврат, доставка, реальный терминал и фискальный контур.

**Статус: инфраструктура и приложение новой сети/CRM закоммичены,
но это НЕ production-ready кассовый продукт.**

## Сборка и приёмка

```bash
git checkout main && git pull --ff-only origin main
corepack enable && pnpm install --frozen-lockfile
pnpm typecheck && pnpm test && pnpm build && pnpm stability:check
```

Порядок новых миграций: 231 затем 232 (после всех предыдущих).
В production не выполнять данные бизнес-smoke на живых клиентах;
запускать на disposable staging с backup/restore.
Никакие реальные PSP-платежи, чеки или устройства кассы в ходе
этой разработки не тестировались.
