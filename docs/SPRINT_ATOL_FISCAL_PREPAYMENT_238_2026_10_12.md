# Спринт 238 — АТОЛ Онлайн, фискализация предоплаты (12 октября 2026)

Изменения закоммичены в `main`, без CI/GitHub Actions.

## Назначение и границы

Сервис уже создаёт платежи YooKassa и регистрирует статус банка.
Теперь можно **явно** указать, кто выполняет фискализацию:
`YOOKASSA` (прежний режим, значение по умолчанию) или
`ATOL_ONLINE` (отдельный АТОЛ API v5, ФФД 1.2).
Провайдер сохраняется в каждом `commerce_payment_intent`; после
создания платежа изменение настроек **не переписывает** его режим.

**До полноценной коммерческой готовности не хватает:**
- чека `full_payment` с зачётом аванса при выдаче товара;
- `sell_refund` для возврата прихода и проверенного сценария
  банковского refund + независимой ККТ;
- поддержки обязательной маркировки по группам товаров,
  кода идентификации/разрешительного режима и документов Честного ЗНАКа;
- автоматического фонового polling ATOL и уведомления о `UNKNOWN/FAIL`;
- реальных sandbox и production E2E с бухгалтером/ОФД.
Все эти сценарии остаются **NO-GO**.

## Функции

1. `infrastructure/postgres/238_atol_fiscal_document_routing.sql`:
   - `commerce_merchant_config.fiscal_provider` — выбранный провайдер
     для **будущих** оплат;
   - `commerce_payment_intent.fiscal_provider` — неизменяемая копия
     принятого маршрута;
   - `commerce_fiscal_document` — по одному `sell` для каждого
     provider payment. Tenant RLS, уникальность внешнего ID/UUID,
     статусы `SENDING/UNKNOWN/WAIT/DONE/FAIL`.
2. `/app/sites/payments`:
   выбор источника чека, по умолчанию YooKassa.
   При АТОЛ receipt object **не** отправляется в YooKassa; иначе
   продавец рисковал бы получить два чека на одну оплату.
3. `/app/settings/integrations/connect`: отдельные
   реквизиты продавца для АТОЛ: ИНН, email, СНО, место расчёта,
   единая ставка НДС для пилота, группа ККТ, защищённые
   credentials, подтверждение авторизации.
4. `AtolReceiptsService`:
   - список подтверждённых YooKassa-платежей без чека АТОЛ;
   - платёж должен быть `SUCCEEDED`, проведён в Finance,
     иметь `fiscal_provider='ATOL_ONLINE'`;
   - вручную подтверждаются немаркируемые/неподакцизные товары;
     при наличии кодов маркировки во внутреннем реестре операция
     блокируется даже с отмеченным флагом;
   - строки чека, цена, количество и сумма собираются из
     серверной `sales_order_line`, сверяются с оплаченными
     копейками. Нельзя передать с фронтенда цену чека;
   - регистрируется `sell` с `payment_method='full_prepayment'`;
   - строка отправляется **только один раз**; после таймаута
     `UNKNOWN`, нужен UUID и ручная сверка кабинета АТОЛ;
   - GET report проверяет внешний `external_id`, UUID,
     совпадение суммы, обязательные ФН, ФД и ФП,
     только затем `fiscal_status='SUCCEEDED'`.
5. После работы банка YooKassa-reconcile не присваивает
   `fiscal_status='SUCCEEDED'` для АТОЛ даже если у банка
   есть собственный статус регистрации чека.
   Финансовое проведение и фискализация независимы.

## Feature flags

По умолчанию **все фискальные POST АТОЛ отключены**:

```dotenv
COREBIZ_ATOL_RECEIPTS_ENABLED=false
COREBIZ_ATOL_PRODUCTION_RECEIPTS_ENABLED=false
```

Приёмочный тест только в отдельной sandbox ККТ и тестовом
YooKassa account: после миграции и проверок изменить **первый**
флаг на true. Второй флаг оставить false до подписанной
приёмки чеков, возвратов и зачёта предоплаты.

Внимание: даже тестовый фискальный `sell` — настоящий запрос
на обработку документа в тестовой среде провайдера; не запускать
его повторно при отсутствии HTTP-ответа.

## API

```text
GET  /api/v1/provider-connectors/sites/:siteId/atol/pending-payments
GET  /api/v1/provider-connectors/sites/:siteId/atol/receipts
POST /api/v1/provider-connectors/sites/:siteId/atol/payments/:paymentId/receipt
POST /api/v1/provider-connectors/sites/:siteId/atol/receipts/:documentId/verify
```

Защита: авторизация и `sites.manage` с scope `all`,
tenant RLS и проверка принадлежности payment/connection/site.
Ключи не выдаются из API клиенту. Отчёт провайдера сверяется
по UUID, external_id и сумме; выданный `fiscal_sign` —
не флаг пользователя в настройках.

## Как проверять перед запуском

1. На чистом staging применить миграции 234–238
   **по порядку**, после резервного копирования.
2. Проверить существующий сценарий YooKassa:
   он по-прежнему передаёт `receipt` и продолжает фискализировать
   чек через свой штатный процесс.
3. Подключить тестовую ККТ АТОЛ; заполнить ИНН/СНО/адрес
   и подтвердить API-токен.
4. В тестовом магазине переключить будущие платежи на АТОЛ.
   Создать тестовый заказ из **немаркируемых** товаров.
5. Убедиться, что банком подтверждён один платёж,
   Finance имеет одну проводку, а YooKassa **не** регистрировала
   чек самостоятельно.
6. Отправить чек АТОЛ, затем получить report. Состояние
   `WAIT` не является успешной фискализацией.
   В `DONE` обязательны корректные ФН/ФД/ФП, exact total
   и совпадающий external_id.
7. Повторить отправку того же `paymentId`, создать HTTP-timeout,
   проверить `UNKNOWN` и невозможность двойного `sell`.
8. Негативные тесты: чужой tenant, sites.read без all,
   поддельный provider_uuid, чужой `external_id`, неверная сумма,
   маркируемый SKU, несовпадение валюты, истекшие credentials.
9. Проверить полный сценарий в бухгалтерии и ОФД **до**
   коммерческого включения и обязательно реализовать
   второй чек полного расчёта и возвраты.

Выпускная проверка на тестовом сервере:

```bash
git checkout main && git pull --ff-only origin main
corepack enable && pnpm install --frozen-lockfile
pnpm db:migrate && pnpm typecheck && pnpm test
pnpm build && pnpm stability:check
```

Не запускались live платёж, документ ККТ, реальный webhook,
миграции PostgreSQL и браузерный E2E в рамках этой работы.
