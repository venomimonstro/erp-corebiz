# CoreBiz — коммерческий GO / NO-GO и контуры интеграций

Дата: 11 октября 2026. Исходники на `main`. Без CI/GitHub Actions.

## Главный вывод

**NO-GO для обещания «полноценная замена 1С/МойСклад/YCLIENTS во
всех нишах».** Можно готовить ограниченный **платный пилот** с
договором, конкретно описанным составом функций и контролируемой
поддержкой. Оплата SaaS CoreBiz и оплата товаров компаний — два
независимых вида платежей, даже если используется одна торговая марка.

В этом аудите обнаружен отдельный ложноположительный критерий:
Go-Live Center проверял бизнес-процессы, но не требовал провайдерский
end-to-end для банковской оплаты, фискального чека, доставки и
маркировки. Это исправлено в исходниках:
- `apps/api/src/modules/platform/go-live/commercial-checkout-policy.ts`
  блокирует торговый GO до появления независимых подтверждений;
- `go-live.service.ts` включает проверки и использует evidence
  **только для утверждённого релиза**;
- unit: `commercial-checkout-policy.spec.ts`.
- Предыдущие общие Go-Live evidence **не означают** PSP/ККТ PASS.
- **Предупреждение:** требуемые категории внешнего evidence пока
  намеренно не регистрируются как «PASS», поскольку для них нет
  проверенных адаптеров и полностью автоматической аттестации.
  Нельзя вручную ставить пользовательский флаг и считать ККТ
  подключённой; нужен настоящий провайдерский ID, проверенный
  внешний ответ и связанный внутренний ledger документ.

## 1. Минимально допустимая первая продажа SaaS CoreBiz

Выделить ограниченный тариф/пилот для ниш **без обещания
полностью автоматических платежей их покупателей, ФНС и ККТ**.

Условия:
- регистрация tenant, приглашённые сотрудники и роли,
  восстановление доступа, пароль, выход со всех устройств;
- опубликованный тариф, лимиты, trial, оплаченный период,
  grace/READ_ONLY без потери данных;
- самостоятельная оплата CoreBiz через **ваш** договор
  эквайринга, подтверждение GET провайдера,
  идемпотентное продление и бухгалтерский документ/чек;
- самопомощь: тариф, история начислений и платежей,
  изменение/отмена подписки, возвраты, счета юрлицам;
- отдельный коммерческий договор/оферта, назначение
  оператора/обработчика персональных данных,
  политика конфиденциальности/согласия, ОРД при рекламе,
  регламент хранения/удаления/выгрузки;
- поддержка (канал, SLA, тикеты), инцидент-менеджмент,
  резервные копии/восстановление и стоимость себестоимости сервиса;
- паспорт пилота и договорённый способ ограничить
  неподтверждённые операции (налоги, ЕГАИС, маркировка, ККТ).

Отдельно проверить статус самозанятости/ИП/ООО и допустимость
первичных бухгалтерских документов для **вашей** модели продаж,
обработку НДС/УСН, чеки и возвраты со специалистом по РФ.
Не выдавать правовое заключение из исходного кода.

## 3. Платежи — строго два изолированных платежных домена

### A. Покупка подписки CoreBiz

**Текущий код:** `BillingService`, `CommercePaymentsService.beginSaas`,
`YooKassaGateway`, `tenant_subscription`, `billing_event`,
`/app/settings/billing`, webhook + GET provider confirmation.

**P0 перед реальными подписками:**
1. Провести sandbox и один контрольный live payment.
2. Финализацию renew подтверждает **провайдер**, а не
   returnUrl; повтор webhook не продлевает период снова.
3. Сверка `commerce_payment_intent` после потери webhook:
   durable worker, backoff, алерт старого PENDING, dead letter.
4. Фискализация SaaS: реальный чек, налоговая ставка,
   признак услуги, реквизиты покупателя; ошибку ККТ обрабатывать
   отдельно от успешного банка.
5. Пробные/кредитные/платные тарифы и ограничения
   `max_users`/branches/warehouses проверять конкурентно в PostgreSQL.
6. Счёт/акт для юридических лиц, возврат за неполный срок
   по условиям договора, paid/grace/read-only, release entitlement.
7. Учёт денег сервиса отделён от денег магазинов клиентов.

### B. Платёж покупателя клиента CoreBiz

- Продавец подключает **свой** merchant account:
  `tenant + site/retail_location`, AES-256-GCM секрет,
  отдельные тарифы, эквайринговые операции, reconciliation.
- Hosted ЮKassa, затем по спросу T-Банк, Сбер,
  CloudPayments, другие. Не нужно подключать сразу пять провайдеров;
  достаточно одного проверенного PSP для первого пилота.
- Offline терминалы: отдельный протокол конкретного банка
  и устройства, не «АТОЛ-терминал».
- Не выдавать `PAID` без provider capture; не отгружать
  по непроверенному банковскому callback.
- Refund, chargeback, manual reconciliation, ФН/ФД/ФП,
  partial refund и цена/НДС строк чека.

Официально о webhook и повторных попытках:
https://yookassa.ru/developers/using-api/webhooks
https://yookassa.ru/developers/using-api/response-handling/recommendations

## 4. ККТ: АТОЛ и Эвотор — разные режимы

1. **Онлайн-сайты**: выбрать первым облачный фискализатор
   АТОЛ Онлайн v5/Эвотор Цифровая касса (ФФД 1.2),
   подключать с seller credentials, коды налогов/НДС и
   ИНН каждой компании. API `register`/GET result,
   callback, повтор/idempotency, журнал `fiscal_document`.
2. **Физическая точка**: приложение/SDK Эвотор,
   фискальный регистратор АТОЛ или драйвер установленной
   ККТ; открыть/закрыть смену, сформировать приход/возврат,
   чек маркированного товара, sync of OFD.
3. **Банковский терминал** — другой контур:
   платёж через Т-Банк/Сбер/другого acquirer; bank capture
   должен совпасть с кассовым receipt и `Finance`.
4. Предоплата онлайн и выдача товара в магазине —
   отдельные события, и может требоваться чек полного расчёта.

https://help.atol.online/article/11244
https://docs.evotor.cloud/docs/api
https://developer.evotor.ru/docs/rest_overview.html

## 5. Честный ЗНАК для электроники в 2026

Для конкретных видов радиоэлектроники в ПП РФ №1954:
- регистрация участников с 01.03.2026 (отдельные группы —
  специальные даты согласно редакции);
- производители/импортёры маркируют товары с 01.05.2026;
- до 30.11.2026 можно реализовать/промаркировать
  определённые дореформенные остатки;
- с 01.12.2026 начинается обязательная передача сведений
  поэкземплярного оборота и ограничения на немаркированные
  остатки соответствующих категорий;
- с 01.03.2027 — передача розничного выбытия
  через ККТ для соответствующих видов радиоэлектроники.

**Электроника в целом не = каждый SKU маркируемый.**
Классификация по коду ОКПД2/ТН ВЭД/действующим датам, а
не по слову «ноутбук» в карточке. Требуются GTIN и Data Matrix
отдельно от serial/IMEI, контроль единиц товара, обмен
ЭДО и статусных событий ГИС МТ, УКЭП/сертификаты
участника, сканеры и разрешительный режим по применимости.
https://markirovka.ru/knowledge/tovarnye-gruppy/radioelektronnaya-produktsiya-noutbuki-i-smartfony/sroki-i-etapy-markirovki-noutbuki-i-smartfony

## 6. СДЭК и Почта России

**СДЭК (первый перевозчик)**:
- договор клиента, clientId/secret, OAuth2 token cache;
- адрес отправителя, вес/габариты каждого SKU, ПВЗ;
- quote → выбор ПВЗ/адреса → snapshot тарифа →
  создание накладной с idempotency → номер и PDF-этикетка;
- статусы принятия/вручения/утраты/возврата, изменения
  тарифов, компенсация после отмены.
- Отправление не создаётся на клиентском browser redirect.
https://developer.cdek.ru/

**Почта России (следом)**:
- договор и доступ «Отправки», application token + user key;
- нормализация адресов, тарификация, создание отправления,
  партии/ярлыки, ШПИ, отслеживание/возврат;
- нужен отдельный `shipping_order` и журнал провайдера,
  не просто текстовое поле tracking.
https://otpravka.pochta.ru/specification

Существующие `commerce_delivery_method` сейчас покрывают
ручной самовывоз и фиксированную местную доставку;
**это ещё не интеграция со СДЭК и Почтой России**.

## 7. Техническое ядро всех новых подключений

Единый стабильный интерфейс:
`Connection` → `Operation` → `ProviderRequest` →
`VerifiedProviderResult` → `DomainLedgerEvent`.

Требования:
- encrypted per-tenant secrets, no raw tokens in logs;
- fixed upstream host (SSRF protection), timeout, retry/backoff;
- uniqueness `(tenant,provider,operation,idempotencyKey)`;
- асинхронные callbacks, дедуп и reconciliation-проход;
- status `DRAFT/CONFIGURED_UNVERIFIED/VERIFIED/DEGRADED/DISABLED`;
- история попыток с редактированными JSON/error;
- регистрация вебхуков с replay-защитой;
- tenant RLS + scopes, квоты и финансовые лимиты;
- sandbox и live секреты отдельно.

## 8. Контроль запуска

1. **Ограниченный платный пилот CRM/ERP** можно обсуждать
   после полного прохождения auth, SaaS PSP, billing,
   RLS, backups/restore, security, support и договора.
   Не обещать работающие ККТ, перевозчиков и ФНС.
2. **Интернет-магазин с оплачиваемой корзиной** —
   только после реальной оплаты/чека/доставки/возврата.
3. **Розничная сеть** — после устройства кассы, bank POS,
   разрешений кассиров по точкам и сверки смен.
4. **Маркируемая электроника** — после подготовки к
   требованиям конкретной товарной группы и ДМ.
5. **Массовый запуск «все ниши»** — только после прохода
   полного Golden/E2E набора и расширенной поддержки.

Для каждого коммерческого разрешения фиксировать доказательства:
commit SHA, версия схемы, идентификатор стенда (без паролей),
тестовый external provider ID, receipt ID, shipment ID, ledger ID,
последняя дата backup restore, сквозная история корреляции,
ответственный и дата проверки.

Важно: в текущем release registry наборы внешних kind
(`PAYMENT_E2E`, `FISCAL_E2E` и другие) пока не
поддерживаются как автоматически подтверждаемые виды
evidence. Поэтому новые go-live блокеры по внешним
провайдерам **не должны становиться PASS до разработки
проверяемых интеграционных адаптеров**. Нельзя
разблокировать GO простой вставкой успешной записи.

## 9. Порядок ближайших спринтов

**P0-SaaS:** webhook recovery + billing reconciliation + фискализация
подписки + полномасштабный auth/security/backup/support.

**P0-магазин:** один продавец / одна ЮKassa / один АТОЛ /
СДЭК / buyer E2E с полной и частичной оплатой и возвратом.

**P0-розница:** ККТ Эвотор/АТОЛ по выбранному железу +
конкретный банковский терминал + права сотрудников точки
+ кассовая сверка.

**P0-электроника:** serial/IMEI + применимая маркировка
+ ЭДО + гарантийные ремонты/возвраты.

**P1-расширение:** Почта России, новые банки, обмен ККТ,
маркетплейсы, автоматизация бухгалтерии, white-label/API.

### Проверка исходников без CI

```bash
git checkout main && git pull --ff-only origin main
corepack enable && pnpm install --frozen-lockfile
pnpm typecheck && pnpm test && pnpm build && pnpm stability:check
```

Эта проверка НЕ заменяет production gate с disposable DB,
реальным backup restore, provider sandbox и HTTP browser E2E.
Реальные внешние API, живые оплаты, ККТ и доставка в текущем
сеансе не тестировались. Статус коммерческого запуска
до этих доказательств: **NO-GO**.
