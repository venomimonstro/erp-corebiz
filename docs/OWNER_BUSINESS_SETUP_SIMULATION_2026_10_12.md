# CoreBiz · реальный путь владельца от регистрации до наполнения (12.10.2026)

**Ветвь:** `main`. Реализованы новые исполняемые проверки,
не GitHub Actions. **Состояние проверки:** статическая валидация маршрутов,
синтаксиса и исходных Nest-контрактов; на этой сессии не было доступа
к disposable API/PostgreSQL/Chromium, поэтому **E2E PASS пока не получен**.

## Персона и сценарии

**Персона А** — владелец небольшого магазина электроники:
приходит впервые, выбирает «Свой интернет-магазин», приглашает
сотрудника, заводит юрлицо/филиал/команду, поставляет ноутбуки и
мыши, настраивает CRM и самовывоз, проверяет публичный каталог.

**Персона Б** — тот же владелец, открывший второе направление:
создаёт отдельную компанию «Салон красоты», заполняет услуги,
мастера и расписание, регистрирует первого клиента и запись,
переключается обратно в магазин без потери данных. Сотрудник
первого бизнеса ничего не должен узнать о втором.

## Точная последовательность исполнения

| № | Проверка от лица пользователя | Проверяемый результат |
|---|---|---|
| 1 | Открыть API и проверить готовность | PostgreSQL, Redis, изоляция готовы |
| 2 | Попробовать открыть кабинет без входа, отправить неправильную регистрацию | HTTP 401/400; чужих данных нет |
| 3 | Зарегистрировать владельца с компанией | Tenant и Owner-membership, действующая сессия |
| 4 | Выбрать ECOMMERCE_STORE | Профиль ECOMMERCE, нужные модули активны |
| 5 | Пригласить сотрудника | Одноразовый токен, зарегистрированный VIEWER, нет права менять каталог/приглашать других |
| 6 | Создать юрлицо, филиал и команду | Все три объекта видны владельцу, сотрудник назначен в команду |
| 7 | Создать CRM-контрагента и сделку | Объекты читаются после записи |
| 8 | Создать склад, два SKU, заполнить себестоимость и продажные цены | 3 ноутбука и 12 мышей отражены в остатках |
| 9 | Создать сайт и настроить самовывоз | Публичный каталог видит оба SKU и цены, checkout знает способ получения |
| 10 | Создать вторую компанию BEAUTY_SALON | Переключение tenant с сохранением строгой изоляции |
| 11 | Добавить услугу, специалиста, рабочие часы, клиента и запись | Бронирование существует, рассчитана стоимость услуги |
| 12 | Проверить изоляцию по компании и вернуться в первую | Другие товары/юрлица/записи не видны; исходные данные сохранены |
| 13 | Выйти, попробовать неверный пароль, зайти повторно | Сессия действительно отзывается, владелец видит обе свои компании |

Проверки не создают настоящих платежей и не обращаются к
YooKassa/СДЭК/Почте России/ФНС. Тестовые email в зоне `.invalid`.
ИНН `1234567894` в disposable-базе — техническая строка с
правильной контрольной цифрой; это **не** регистрация в ФНС
и **не** готовность к фискализации. Если тест обнаружит ошибку,
он завершится с ненулевым exit-кодом и укажет конкретный этап.

## Исполнение на изолированном стенде

**Не запускать на рабочем сервере с production-базой!** Скрипт создаёт
две компании, сотрудника, реальные доменные записи, товар, остатки и
бронирование. Убедиться, что API использует только disposable PostgreSQL,
а не production `DATABASE_URL`.

```bash
git checkout main && git pull --ff-only origin main
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_BASE_URL=http://127.0.0.1:4000 \
COREBIZ_SMOKE_WEB_ORIGIN=http://localhost:3000 \
node scripts/owner-business-setup-e2e.mjs
```

Для браузерной части, отдельно установив Playwright и Chromium в
тестовой среде, выполнить:

```bash
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_WEB_URL=http://localhost:3000 \
node scripts/smoke-browser-journey.mjs
```

Полный gate `scripts/production-gate.sh` теперь **выполняет**
`owner-business-setup-e2e.mjs` до Golden workflows и нагрузки 100
пользователей. На каждом запуске выходной JSON фиксирует этапы, HTTP,
латентность, созданные типы объектов и число проверок **без паролей,
cookie, приватных токенов**.

## Что обнаружено и исправлено при подготовке

1. В старой браузерной симуляции после регистрации ожидалась
   страница `/app`, хотя актуальная регистрация требует нишу и
   переводит в `/app/start`. Исправлены переходы и селекторы.
2. Предыдущая owner-first-day симуляция не проверяла приглашение,
   ограничения роли, назначение команды, контрагента/CRM,
   вторую бизнес-нишу и переключение компании. Внедрён отдельный
   полноценный сценарий.
3. `OrganizationService.createLegalEntity` пропускал ввод
   произвольного некорректного ИНН/КПП. Добавлены проверка контрольных
   цифр ИНН (10/12 знаков), формат КПП, защита от нестроковых
   входных данных, негативные регрессионные тесты. Пустые реквизиты
   допустимы для черновика; реальную принадлежность проверяет ФНС.

## Остающиеся ограничения и критерии GO

- Реальный sandbox API, миграции, доступ к тестовой БД и Chromium
  в этой сессии отсутствуют: **прошедших живых проверок 0**.
- Для сети магазинов надо отдельное E2E с филиалами, кассами
  АТОЛ/Эвотор, маркировкой и резервами между точками.
- Для услуг — отдельное E2E зарплат, отмен/неявок и оплаты визитов.
- Для бухучёта — отдельное ручное подтверждение ИНН, системы
  налогообложения, платежей/чеков и сроков ФНС.
- Нагрузочная стабильность 99,9% доказывается независимо за 30
  дней, а не одним успешным «первым днём».

**Release-вердикт:** новая симуляция написана и добавлена в gate,
но production-коммерческий GO **не подтверждён** без её реального
выполнения, анализа результатов, проверки интеграций и restore.
