# CoreBiz — приглашения сотрудников и дорожная карта касс, маркировки, оплаты и доставки

Дата: 11 октября 2026. Изменения — в `main`, без CI/GitHub Actions.

## 1. Реализовано: приглашение участника в существующую компанию

### Владелец компании

1. `/app/settings/team` → укажите email → роль → «Создать ссылку приглашения».
2. `POST /api/v1/tenants/invite` (permission `users.manage`, только `all`
   внутри service): случайный токен хранится **только в виде хэша**,
   действует семь дней, предыдущие ожидающие ссылки на этот email
   отзываются. Токен возвращается владельцу **ровно один раз**,
   с `Cache-Control: private, no-store`.
3. Ссылка вида `https://<WEB_ORIGIN>/invite#token=<TOKEN>`
   не пересылает bearer-secret в HTTP-path/query к серверу.
   Владелец копирует и отправляет её вручную. **SMTP email-доставки
   пока нет**; UI об этом предупреждает.
4. В интерфейсе видны действующие и исторические приглашения;
   ожидающие можно отозвать.
5. Роль `OWNER` никогда не может назначаться по приглашению.
   `roleId` выбирается только тем, у кого есть `roles.manage`
   на всю организацию; non-owner не может делегировать права
   выше собственных. Без roleId пользователь получит VIEWER.
6. Список участников и назначение роли из `/roles/assign`
   работают через существующий RBAC с проверкой роли владельца.

### Приглашённый сотрудник

- **Есть аккаунт:** перейти по ссылке, войти, нажать
  «Принять приглашение»; затем активируется существующая компания.
- **Нет аккаунта:** указать email из приглашения и новый пароль.
  `POST /api/v1/auth/register-invited` (rate-limited), Argon2id,
  приём хэшированного токена, атомарное создание member/session.
  **Новая компания и собственная подписка не создаются.**
- Проверяется реальный email `app_user` из БД, а не произвольный
  адрес из тела API; нужен активный tenant, неистёкший PENDING invite.
- SQL функция `corebiz_auth_accept_invitation` блокирует токен
  `FOR UPDATE`, запрещает OWNER, выдаёт роль в той же транзакции,
  не сохраняет приглашение если создание user/member не получилось.
- Миграция `233_invitation_roles_and_accept.sql`.

### Что остаётся до финального запуска приглашений

- SMTP/транзакционный email-сервис с SPF, DKIM, DMARC,
  очередью доставки, retries, антифрод-лимитами, шаблонами
  и подтверждением домена.
- Настройка **доступа сотрудника к конкретной retail_location**
  и ограничение списка складов/заказов/финансов на API,
  не только скрытие меню. `VIEWER` — не кассир.
- Онбординг приглашённого в нужный workspace,
  деактивация staff-сессий при отзыве membership,
  мониторинг запущенного сервера и real-browser E2E.
- Инвайты не должны открывать оплаченные функции SaaS сверх
  политики количества рабочих мест/плана.

## 2. Интеграции: разные типы провайдеров — разные подтверждения

**Не объединять терминал, банк, кассу и доставку в один "успешный" статус.**

Сценарий продажи:
1. Заказ подтверждён и товар зарезервирован `OMS/Inventory`.
2. Отдельный банковский provider подтвердил payment capture;
   только затем одно финансовое проведение `Finance`.
3. ККТ подтвердила фискальный документ/чек, его реквизиты
   сохранены в idempotent fiscal-ledger.
4. Если товар подлежит обязательной маркировке —
   код проверен, выбытие проведено согласно применимому
   регламенту и сохранено состояние внешнего запроса.
5. Подтверждён заказ перевозчика, получены номер отслеживания,
   ярлык; внешние статусы ведут shipment, не подменяя статусы оплаты.
6. Возврат согласован по товару, оплате, фискальному чеку,
   маркировке и перевозчику. Повтор webhook не выполняет возврат дважды.

### АТОЛ Онлайн (облачная ККТ)

- Что нужно клиенту: договор/регистрация ККТ, данные доступа к API,
  идентификатор группы ККТ, настройки СНО/НДС и ФФД.
- Backend: отдельный адаптер АТОЛ с fixed-base URL,
  `fiscal_document` с типом (приход, возврат, зачёт предоплаты),
  корреляцией по SalesOrder/Payment, уникальными идемпотентными
  операциями и долгоживущей очередью callback/poll.
- Квитанция фискализации — **не** событие оплаты; статус
  `SUCCEEDED` — только после провайдера.
- Для маркированного товара нужна проверка поддержки ФФД 1.2;
  ставки НДС и реквизиты проверять по актуальной спецификации.
- Референсы:
  https://help.atol.online/article/11244
  https://help.atol.online/article/26152

### Эвотор (смарт-терминалы) и Цифровая касса

- **Облако Эвотор**: приложение разработчика, согласие магазина,
  token, синхронизация товаров, чеков и смены, reconciliation с
  CoreBiz по `store_id`/retail_location.
- **Цифровая касса**: отдельный фискальный API,
  логин/пароль/группа ККТ, callback и polling, подтверждение
  фискального документа и ошибок ФН.
- Нужна реальная касса/тестовый доступ от Эвотор. Не путать
  ККТ с банковским платежным терминалом и не учитывать
  чек `SELL` как доказательство банковского capture.
- Документация:
  https://developer.evotor.ru/docs/
  https://developer.evotor.ru/docs/rest_api_get_store_documents.html
  https://docs.evotor.cloud/docs/api

### Банковские платежные POS-терминалы

- Поддержка **по конкретной модели и эквайеру**: терминал Сбер,
  Т-Банк и т. д. не имеет единого общего протокола «АТОЛ/Эвотор».
- Клиенту нужны договор эквайринга, merchant/terminal ID,
  документы API/SDK либо драйвер интеграции, фискальный контур.
- Обязательны capture/cancel/refund, trace/RRN,
  двойная сверка: терминал → банк → Finance,
  повторные callbacks и разрыв связи. Платёж `PENDING`
  не закрывает заказ.

### Онлайн-платежи для покупателей

- **ЮKassa уже имеет источник кода интеграции в CoreBiz**:
  отдельный shop ID/secret на сайт, provider payment intent,
  сверку webhook с GET провайдера и Finance-ledger.
- Нужно подтвердить тестовый и реальный платежи/возвраты,
  провал фискализации, частичную/повторную оплату,
  возврат денег и закрывающий чек.
- Чтобы добавить Т-Банк/Сбер/CloudPayments/Robokassa,
  вводим uniform PaymentProvider интерфейс `create/get/refund`,
  sandbox и encrypted credentials каждого магазина,
  не меняя Finance/OMS/витрину.
- НЕ писать логин банка/ключ клиента в общие frontend logs;
  не подтверждать заказ по browser redirect.
- https://yookassa.ru/developers/using-api/webhooks
  https://yookassa.ru/developers/payment-acceptance/getting-started/quick-start

### Честный ЗНАК (маркировка)

- Определяется **товарной группой** и правовым режимом,
  а не категорией «электроника» целиком. Для ноутбуков,
  смартфонов и других радиотоваров проверять актуальный
  календарь обязательств конкретного GTIN/товарной группы.
- Нужны регистрация в ГИС МТ, УКЭП, полномочия участника,
  интеграция True API, Национального каталога и СУЗ по
  операциям/группам, поддержка сканера Data Matrix.
- Продукту нужны serial/IMEI **отдельно** от кода
  маркировки, учёт кодов по единицам SKU, движениям и возвратам.
  Запрещать выдачу маркированного товара без необходимых
  подтверждений, где закон требует проверки.
- Документация доступна в промышленном личном кабинете
  системы маркировки, раздел «Помощь»:
  https://markirovka.ru/knowledge/tovarnye-gruppy/radioelektronnaya-produktsiya-noutbuki-i-smartfony/integratsiya-sistemy-markirovki-s-tovarouchetnoy-sistemoy-uchastnika-ikra

### СДЭК (API v2)

- Клиент получает договор/API credentials, sender location,
  правила наложенного платежа/страховки.
- Backend: OAuth 2.0 client_credentials с кэшем токена,
  тариф `POST /v2/calculator/tarifflist`, ПВЗ/постаматы,
  создание заказа `POST /v2/orders`, tracking,
  ярлык, возвраты и собственный carrier-request journal.
- Инвентарь не отгружать и клиента не обнадёживать по
  «вручную введённому трек-номеру»: создание перевозчиком
  и подтверждение принятия — разные состояния.
- https://developer.cdek.ru/

### Почта России

- Онлайн-сервис «Отправка»: договор, токен приложения
  и ключ авторизации пользователя, только HTTPS.
- По официальной API спецификации: нормализация адреса
  и ФИО, тарификация, создание заказа/партии, ярлык,
  ШПИ/отслеживание, отмена, возвращённые отправления.
- https://otpravka.pochta.ru/specification

## 3. Предлагаемая модель данных

Для всех провайдеров:
- `provider_connection`: tenant, site/retail_location,
  provider, secret (AES-GCM; никакого raw credential в UI),
  status `DRAFT/CONFIGURED_UNVERIFIED/VERIFIED/DISABLED/ERROR`.
  Нельзя переводить в VERIFIED без реального round-trip с API.
- `provider_operation`: бизнес-документ, тип операции,
  idempotency key, request hash, provider transaction ID,
  last provider status, attempt counters, next retry.
- `fiscal_document`: тип чека, банк/наличные, позиции,
  код маркировки, ФН/ФД/ФП, статус ОФД.
- `shipping_order`: продажи/корзина, выбранный ПВЗ,
  перевозчик, точная цена, накладная, статус, tracking,
  запрет многократного создания без идемпотентности.
- `marking_unit`: GTIN/SKU/serial/IMEI, Data Matrix,
  товарная группа, уникальный код, статус введения/выбытия.

Не объединять статусы `payment_succeeded`,
`fiscal_succeeded`, `shipment_accepted` и `delivered`.

## 4. Порядок реализации

- **Спринт A (сейчас)**: приглашения, права, отзыв, одноразовая
  ссылка, регистрация приглашённого и пользовательский экран
  требований к провайдерам.
- **Спринт B (P0)**: store-scoped RBAC для кассира/кладовщика,
  уязвимости доступа через API, SMTP invitation delivery,
  модели токенов/подключений и test harness без реального списания.
- **Спринт C (P0)**: полноценная онлайн-оплата и фискализация
  АТОЛ/Цифровая касса, возвраты и reconciliation.
- **Спринт D (P0)**: СДЭК, затем Почта России с расчётом стоимости,
  ПВЗ/ОПС, label и shipping webhooks.
- **Спринт E (P0 для маркируемых товаров)**: Честный ЗНАК,
  Data Matrix/serial и касса ФФД 1.2.
- **Спринт F**: банк-эквайринг офлайн, конкретный SDK терминала,
  сверка банковского и кассового отчёта по точке, мониторинг.

## 5. Нельзя обещать до реальных проверок

В этой сессии **не запускались** production Postgres миграции,
email SMTP, настоящее ККТ/банковский терминал, API СДЭК/Почты,
подпись УКЭП, операции маркировки и внешние отправления.

Новый UI `/app/settings/integrations` называет доступной настройку
ЮKassa, остальные провайдеры маркирует `ADAPTER_REQUIRED`.
Он не принимает секреты неработающих провайдеров и не имитирует
успешную проверку подключения.

Сначала применить миграцию `233_invitation_roles_and_accept.sql`
на disposable staging PostgreSQL с резервной копией, затем
прогнать typecheck, tests и браузерные E2E на двух аккаунтах
(пригласивший и приглашённый), в том числе одновременный accept
одного токена и запрет роли OWNER.
