# CoreBiz — целостность студии танцев: направления и группы
Дата: 14 октября 2026 года · Репозиторий: venomimonstro/erp-corebiz · Ветка: main

## Назначение

Для студии из двух филиалов, 12 направлений и 52 тренеров добавлен
**полный управляемый цикл направлений и групп**. Важное архитектурное
условие: цена, длительность, клиент, тренер, зал и финансовые движения
остаются в общих CoreBiz-модулях, а не копируются в «отдельную ERP танцев».

| Объект | Создать | Посмотреть | Изменить | Архивировать | Восстановить |
|---|---|---|---|---|---|
| Направление | POST /dance/programs | GET /dance/programs | PATCH /dance/programs/:id | POST /dance/programs/:id/archive | POST /dance/programs/:id/restore |
| Группа | POST /dance/groups | GET /dance/groups | PATCH /dance/groups/:id | POST /dance/groups/:id/lifecycle (ARCHIVE) | тот же endpoint (RESTORE) |
| Услуга общего каталога | POST /service/catalog | GET /service/catalog | PATCH /service/catalog/:id | POST /service/catalog/:id/archive | POST /service/catalog/:id/restore |
| Тренер / зал | POST /service/resources | GET /service/resources | PATCH /service/resources/:id | POST /service/resources/:id/archive | POST /service/resources/:id/restore |

Вместо физического DELETE используется ARCHIVED; записи, абонементы,
финансовые документы и история посещений остаются доступны для аудита.

## Рабочий путь владельца

1. **Направления:** `/app/dance/directions` → «Создать направление» →
   выбрать активную услугу из единого каталога, филиал, название,
   возраст, длительность → сохранить.
2. **Группа:** `/app/dance/groups` → связать направление с тренером,
   залом, календарём, вместимостью и порогом окупаемости.
3. **Ученик и абонемент:** `/app/dance/students`, затем
   `/app/service/packages` → выбрать плательщика и программу.
4. **Занятие:** расписание и участников сверяет backend; оплата,
   задолженность и списание абонемента обрабатываются существующими
   общими учётными механизмами.
5. **Изменить направление:** изменить название/длительность; при
   необходимости указать другую услугу или филиал. Существующие
   группы защищены от небезопасной смены услуги, филиала и возрастных
   ограничений. Настройки редактируются через optimistic revision.
6. **Завершить группу:** сначала снять активное участие учеников,
   обработать лист ожидания и перенести/отменить будущие занятия.
   Затем архивировать группу с ожидаемой версией.
7. **Закрыть направление:** только после урегулирования групп и
   будущих занятий. История остаётся без изменений.
8. **Вернуть направление:** восстановление требует существующей
   активной услуги общего каталога. Группа после восстановления
   становится **черновиком DRAFT**, а не немедленно доступной к записи.
   Её расписание, зал, персонал и цену надо перепроверить вручную.

## Проверки ошибок

- **Чужой филиал:** сервер проверяет tenant_id у branch и отклоняет.
- **Старая карточка:** сервер сравнивает revision направления или
  числовой version группы и возвращает конфликт.
- **Неверный возраст или длительность:** BadRequest до изменения БД.
- **Менеджер без catalog.write:** не может создавать, переоценивать
  или архивировать направления.
- **Активные ученики:** блокируют архивирование группы.
- **Будущие занятия:** блокируют архивирование группы/направления.
- **Лист ожидания:** нельзя исчезнуть, пока он не обработан.
- **Связанная услуга архивирована:** направление не восстанавливается.
- **Уволенный тренер:** группу нельзя восстановить без действующего
  специалиста; будущие назначения требуют переноса.
- **Роль тренера с own scope:** GET направлений ограничен его группами,
  других преподавателей не показывает.

## Какие части ОБЩИЕ для остальных ниш

- `service_catalog_item` и lifecycle услуг используются также
  салонами, автосервисами, сервисными компаниями.
- `service_resource` и lifecycle ресурсов применимы к мастерам,
  механикам, кабинетам, креслам и залам.
- `service_booking` остаётся общей системой резервирования с
  транзакционной проверкой доступности и идемпотентностью.
- CRM/Party — единая клиентская база, финансы и начисления —
  отдельные контуры с RBAC и audit_event.
- `dance_program` и `dance_group` — **только отраслевые
  представления**, добавляющие семейные группы, расписание и
  посещаемость, а не второй независимый учёт услуг.

## Воспроизведение на изолированном стенде

```bash
git checkout main && git pull --ff-only origin main
pnpm typecheck && pnpm test && pnpm build
pnpm test:dance:owner
```

Далее для одноразовой PostgreSQL и изолированного Redis:

```bash
COREBIZ_CONFIRM_DISPOSABLE_DB=YES \
COREBIZ_SMOKE_BASE_URL=http://127.0.0.1:4000 \
COREBIZ_SMOKE_WEB_ORIGIN=http://localhost:3000 \
pnpm test:dance:owner:e2e
```

**Нельзя запускать E2E на production:** сценарий создаёт компании,
пользователей, сотрудников, договоры, абонементы и занятия.

## Что ещё требует доработки для полноценного клиента

2. Договоры субаренды малых залов, подтверждения оплаты,
   депозитов, отмен, расчёта штрафов и задолженности.
3. Реальное обновление календаря тренеров после переносов, кабинеты
   клиентов с оплатой через sandbox эквайринга.
4. Уровень доступа совладельцев и права менеджеров на конкретный
   филиал, а не всю сеть.
5. Финансовое закрытие месяца: аренда второго филиала, зарплаты
   52 тренеров, налоги, возвраты и сезонность.
